# Exeris Kernel v0.6 — raport sprintów i mapa implementacji

> Data opracowania: 2026-04-15  
> Zakres: open-core / foundation / community  
> Podstawa: `docs/ROADMAP.md`, `docs/architecture.md`, dokumenty subsystemów i ADR

---

## Cel dokumentu

Ten raport porządkuje zakres wersji **v0.6** na konkretne sprinty wykonawcze oraz pokazuje minimalną, bezpieczną kolejność wdrożenia zgodną z roadmapą i bieżącą architekturą repozytorium.

Najważniejsza zasada dla v0.6:

- najpierw **poprawność kontraktów i TCK**,
- potem **uszczelnienie Security i Flow**,
- następnie **transport/runtime uplift**,
- na końcu **quality gates oraz audit dokumentacji**.

---

## Streszczenie wykonawcze

Wersja **v0.6** powinna zostać domknięta w **5 sprintach**, z czego dwa pierwsze są krytyczne dla poprawności i zgodności kontraktowej:

1. **Sprint 1 — Flow correctness**
2. **Sprint 2 — TCK closure i Security contracts**
3. **Sprint 3 — Transport uplift I**
4. **Sprint 4 — Transport uplift II**
5. **Sprint 5 — Quality gate i release hardening**

Największe ryzyka v0.6:

- semantyka retencji terminal states w Flow,
- restart-aware wake dla choreografii,
- brakujące abstract TCK i Community bindings,
- etapowa migracja Community transportu na ścieżkę FFM bez naruszenia The Wall,
- dokumentacyjny dryf między open-core i target-state enterprise.

---

## Założenia architektoniczne

Plan zakłada utrzymanie następujących ograniczeń:

- **SPI pozostaje implementation-blind**,
- **Core pozostaje driver-agnostic**,
- Community może używać Core jako wspólnej infrastruktury, ale bez naruszania granic modułowych,
- każda nowa zmiana widoczna kontraktowo wymaga pokrycia w **Abstract TCK** oraz powiązania w Community,
- fallbacki zgodnościowe, w szczególności dla transportu, pozostają jawnie wspierane.

## Sprint 1 — Flow correctness

### Zakres

1. **Terminal-State Catalog Bounded Retention**
   - zaprojektować politykę retencji dla terminal state catalog,
   - dodać limit w konfiguracji Flow,
   - zagwarantować, że usuwanie wpisów nie odblokuje ponownego wykonania flow zakończonego terminalnie.

2. **Cross-Restart Choreography Wake**
   - rozszerzyć lookup parked o fallback do snapshot store,
   - utrzymać szybki in-memory path jako podstawowy,
   - dodać testy restart-aware wake/recovery.

3. **Flow shutdown telemetry**
   - wdrożyć zdarzenie shutdown dla Flow engine,
   - zapewnić użyteczne pola operacyjne i zgodność z kontraktem JFR.

### Deliverables

- Flow zachowuje poprawność po restarcie runtime,
- retencja nie rośnie bez końca bez kontroli,
- ścieżka zamknięcia engine ma obserwowalność telemetryczną.

### Ryzyka

- źle dobrana polityka retencji może naruszyć idempotencję,
- fallback snapshot store może pogorszyć semantykę wake, jeśli nie zostanie jasno ograniczony do miss path.

### Exit criteria

- testy Flow lifecycle przechodzą,
- restart-aware choreography jest pokryte testem,
- shutdown event jest emitowany i walidowany.

## Sprint 2 — TCK closure i Security contracts

### Zakres

1. **Brakujące bindy Flow TCK**
   - Community binding dla IdempotencyGuard,
   - Community binding dla zero-allocation / bounded-allocation ścieżki scheduler hot path.

2. **CitadelGuard TCK**
   - abstract TCK dla kontraktu RBAC został domknięty,
   - Community binding istnieje i weryfikuje deny semantics oraz EX-SEC-2003.

3. **StorageContextBridge TCK**
   - standalone abstract TCK został dodany,
   - potwierdzono SHARED-only derivation,
   - fail-closed zachowanie dla błędnych danych wejściowych jest egzekwowane testem.

### Deliverables

- wszystkie widoczne kontrakty Security i Flow mają wspólną egzekucję TCK,
- Community binding staje się pełnym dowodem zgodności zachowania.

### Ryzyka

- bez tych testów milestone v0.6 pozostaje niepełny kontraktowo,
- pojawi się dryf między implementacją a dokumentacją subsystemów.

### Exit criteria

- nowe abstract TCK dla Security istnieją i przechodzą,
- Community bindings są obecne dla ścieżek CitadelGuard oraz StorageContextBridge,
- brak regresji w istniejących suite’ach Security/Flow.

## Sprint 3 — Transport uplift I

### Zakres

1. **MPSC ingress handoff**
   - wprowadzić lock-free kolejkę dla aktywnego Community ingress path,
   - poprawić handoff między carrier loop i VT,
   - utrzymać PAQS i obecny model load shedding.

2. **Pinning i throughput verification**
   - potwierdzić brak regresji pinningu,
   - wykonać sustained ingress tests oraz regression checks.

### Deliverables

- ingress handoff jest bardziej przewidywalny i mniej podatny na blokowanie,
- transport zachowuje semantykę priorytetów oraz brak naruszeń concurrency contract.

### Ryzyka

- zła kolejka lub zły model współbieżności może wprowadzić trudne do wykrycia race conditions,
- zależność od zewnętrznej implementacji kolejki musi pozostać szczegółem Community, nie SPI.

### Exit criteria

- brak regresji pinningu,
- testy load-shed i sustained ingress przechodzą,
- brak przecieków implementacyjnych do Core/SPI.

---

## Sprint 4 — Transport uplift II

### Zakres

1. **Community socket path migration to Core FFM syscalls**
   - stopniowe przejście z podstawowych prymitywów NIO na wspólną ścieżkę FFM,
   - użycie Core-provided syscall loading,
   - utrzymanie NIO jako jawnego fallbacku kompatybilnościowego.

2. **Cross-platform validation**
   - obowiązkowa walidacja Linux,
   - zgodność Windows dla ścieżki Winsock,
   - potwierdzenie boot, bind, connect, ingress i load-shed behavior.

### Deliverables

- Community transport wykorzystuje bardziej docelową warstwę socket runtime,
- repo pozostaje zgodne z aktualną roadmapą i kierunkiem architektonicznym.

### Ryzyka

- to najbardziej ryzykowny technicznie obszar v0.6,
- wymaga wdrożenia etapowego oraz ochrony fallbackiem.

### Exit criteria

- Linux validation jest obowiązkowo zielone,
- Windows compatibility nie wykazuje regresji kontraktowych,
- fallback NIO pozostaje dostępny i testowalny.

## Sprint 5 — Quality gate i release hardening

### Zakres

1. **PMD / suppression reduction**
   - sklasyfikować suppressions jako uzasadnione, tymczasowe albo usuwalne,
   - zredukować dług bez naruszenia performance contract.

2. **SonarQube baseline**
   - wdrożyć baseline quality gate dla open-core,
   - zablokować nowe krytyczne regresje i blocker findings.

3. **Open-core / Enterprise separation audit**
   - oczyścić język roadmapy i dokumentacji,
   - oznaczyć co jest: implemented, planned, enterprise-only, out-of-repo.

### Deliverables

- release v0.6 ma mierzalne quality gates,
- dokumentacja opisuje rzeczywisty stan repozytorium,
- open-core roadmap nie miesza target-state z aktualnym wdrożeniem.

### Exit criteria

- audit suppressions zakończony,
- SonarQube baseline aktywny,
- dokumentacja i roadmapa są spójne terminologicznie.
