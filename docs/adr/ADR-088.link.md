# ADR-088 — Cryptographic License Manifest Format and Offline Verification (link stub)

**Authoritative copy:** [`exeris-docs/adr/ADR-088-cryptographic-license-manifest-and-offline-verification.md`](https://github.com/exeris-systems/exeris-docs/blob/main/adr/ADR-088-cryptographic-license-manifest-and-offline-verification.md)

ADR-088 is a cross-repository decision owned by `exeris-docs` that specifies the canonical schema of `license-manifest.json` (v1), deterministic canonicalization using RFC 8785 (JSON Canonicalization Scheme - JCS), and asymmetric digital signature verification using Ed25519 (RFC 8032) verified offline against an embedded `TrustedIssuerKeyStore` during Phase 0 of the kernel bootstrap.

## Why this stub exists

The kernel must enforce license authenticity without third-party JSON/crypto dependencies or outbound network connections (strict air-gap isolation). This stub links the authoritative ADR specification in `exeris-docs` so kernel engineers and automated reviewers understand the cryptographic constraints bound into `exeris-kernel-core`.

## What is adopted in exeris-kernel

- **RFC 8785 (JCS) Canonicalization:** `eu.exeris.kernel.core.contract.crypto.JsonCanonicalizer` sorts keys by UTF-16 code unit, strips whitespace, and serializes every number as an IEEE-754 double the way ECMAScript `Number.prototype.toString` does, with zero external dependencies. Input with no single canonical form is rejected: malformed UTF-8, unpaired surrogates, duplicate keys, non-ASCII digits and numbers outside the double range. Its tests carry the RFC 8785 Appendix B number vectors and the §3.2.2 and §3.2.3 examples.
- **Detached Signature Exclusion:** The top-level `"signature"` section is excluded from the canonical payload. The manifest is parsed once, and the bytes verified are the canonical form of the same tree the contract is read from.
- **Ed25519 Offline Verification:** Verification uses standard JDK crypto (`java.security.Signature.getInstance("Ed25519")`) with 32-byte public keys and 64-byte Base64-encoded signatures.
- **Strict v1 schema:** every field of ADR-088 §1 is checked for its exact type and enumeration; nothing is coerced, truncated or defaulted below the level ADR-089 assigns. `$schema` must name the v1 schema, `signature.algorithm` and `signature.canonicalization` must read exactly `Ed25519` and `RFC-8785`, and an omitted enforcement rule takes `HARD` for capability and environment, `SOFT` for instances and `AUDIT` for the workload envelope. Every violation fails with `EX-LIC-0001`.
- **Embedded Trust Root:** `eu.exeris.kernel.core.contract.crypto.TrustedIssuerKeyStore` holds the issuer public keys as an immutable map fixed at build time, with no mutator, so no code in the process can add or replace a trust root. The bootstrap path resolves keys only there; `LicenseManifestVerifier.verify(…, IssuerKeyResolver)` verifies against a caller-held key (tests) and its result is never bound into the kernel scope. It holds one epoch key, `exeris-root-2026-k1`.
- **Phase 0 Bootstrap Gate:** The manifest is resolved and verified by `ContractBootstrapStep`, a step of `KernelBootstrap.boot()` that runs after configuration and before any subsystem is initialized (ahead of the FOUNDATION phase), so a refused boot has allocated no off-heap memory and bound no socket. The manifest file is named by the configuration key `license.manifest.path`; when that key is set, a missing or unreadable file stops the boot. Otherwise `license-manifest.json` is read from the working directory, then from the classpath. A manifest above 64 KiB is refused.

## When to consult ADR-088

- Any changes to `license-manifest.json` parsing, canonicalization, or signature verification logic.
- Rotation or addition of issuer signing keys in `TrustedIssuerKeyStore`.
- Any modification to error codes `EX-LIC-0001`, `EX-LIC-0002`, `EX-LIC-0003` or `EX-LIC-0006`.
