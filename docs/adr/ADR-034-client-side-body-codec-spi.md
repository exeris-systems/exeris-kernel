# ADR-034: Client-Side Body Codec SPI — `HttpRequestBodyEncoder` / `HttpResponseBodyDecoder` + `KernelWebClient` Facade

**Status:** Accepted
**Date:** 2026-05-19
**Owner:** kernel/transport
**Visibility:** public
**Scope:** kernel/transport (per-repo; lockstep cross-repo coordination with `exeris-tooling`)
**Authors:** Arkadiusz Przychocki
**Supersedes:** ADR-026 — Client-Side Application API (`CommunityWebClient`)

## Context

ADR-026 (Amendment 2026-05-17) corrected the original Sprint 2 placement of the client-side typed HTTP facade and landed it as `CommunityWebClient` in `exeris-kernel-community` under `eu.exeris.kernel.community.http.client`. That amendment fixed three real problems (tier alignment, namespace consistency, `Community*` class-prefix convention) but it left a fourth problem un-addressed that only surfaced once the downstream consumer in `exeris-tooling` was re-read end-to-end:

**`exeris-tooling/KernelClientGenerator` is tier-neutral by definition** — it emits per-entity REST clients (`WidgetClient.findById(id)`, `WidgetClient.create(widget)`, etc.) that compile against the kernel artifact selected by the application's POM. The generator does not know whether the consuming application runs on the Community tier (HTTP/1.1 + HTTP/2) or on the Enterprise tier (HTTP/3 + Panama JSON, when that ships). Its job is to emit code that works against whichever kernel artifact is on the classpath.

The amended ADR-026 forces the generator to hard-code a `Community*` symbol in every emitted client file (`KernelClientGenerator.java` lines 35–38):

```java
private static final ClassName WEB_CLIENT =
        ClassName.get("eu.exeris.kernel.community.http.client", "CommunityWebClient");
private static final ClassName WEB_CLIENT_EXCEPTION =
        ClassName.get("eu.exeris.kernel.community.http.client", "CommunityWebClient", "WebClientException");
```

Emitted code therefore reads:

```java
public final class WidgetClient {
    private final CommunityWebClient client;            // tier-identity in user code
    public WidgetClient(CommunityWebClient client) { ... }
    public Optional<Widget> findById(UUID id) {
        try { return Optional.ofNullable(client.get(...)); }
        catch (CommunityWebClient.WebClientException ex) { ... }  // tier-identity in catch
    }
}
```

The tier name (`Community`) leaks into every application class generated by the tooling. This is a build-time analogue of The Wall (ADR-006): the kernel boundary visible to applications must be implementation-blind. The original ADR-026 amendment treated the generator as a downstream string-substitution problem ("update the FQN constants in lockstep"); on second reading the symptom is structural — the generator's output references a kernel symbol that **encodes tier identity in its name**.

The secondary observation is the symmetry break with server-side. The server-side typed binding seam has been an **SPI** since 0.5.0 (ADR-009 era):

- `HttpResponseBodyEncoder` SPI (`exeris-kernel-spi/.../http/HttpResponseBodyEncoder.java`)
- `HttpResponseEncodingContext` record
- `HttpResponseBodyEncoderRegistry` functional interface with `empty()` static factory
- `HttpEncodedBody` record (reusable carrier)
- Community-side `JsonBodyEncoder` (Jackson 3) as the bundled default implementation

Client-side has no such SPI today. Body marshalling is hard-wired inside `CommunityWebClient.buildRequest` (Jackson `mapper.writeValueAsBytes`) and inside `CommunityWebClient.parseBody` (Jackson `mapper.readValue`). The constructor exposes `ObjectMapper` directly, which both pins Jackson and forecloses on alternative formats (Protobuf, CBOR, Panama-native JSON in a future Enterprise build).

This ADR closes both problems together: it introduces the missing symmetric SPI **and** lifts the facade out of the Community tier into the tier-neutral Core module so that `KernelClientGenerator` can reference a symbol that does not encode tier identity.

## Decision

**Introduce a symmetric client-side body codec SPI in `eu.exeris.kernel.spi.http` (6 new types), wire two new `ScopedValue` provider slots in `HttpKernelProviders`, ship a Jackson-backed Community driver implementing both new registries, replace `CommunityWebClient` with a tier-neutral `KernelWebClient` facade in `exeris-kernel-core` under `eu.exeris.kernel.core.http.client`, and update `exeris-tooling/KernelClientGenerator` in lockstep so emitted code references `KernelWebClient` (no tier identity in the user-visible symbol).**

### 1. SPI surface (new, in `eu.exeris.kernel.spi.http`)

Six new types, all in `exeris-kernel-spi`, added at 0.8.0. Shape mirrors the existing server-side encoder triplet for review and grep symmetry.

```java
// Request encoder — caller payload → off-heap encoded body.
public interface HttpRequestBodyEncoder {
    boolean supports(Class<?> payloadType);
    HttpEncodedBody encode(Object payload, HttpRequestEncodingContext context);
    default int priority() { return 0; }
}

// Request encoding context: method + path + allocator.
public record HttpRequestEncodingContext(
        HttpMethod method,
        String path,
        MemoryAllocator allocator
) {
    public HttpRequestEncodingContext {
        Objects.requireNonNull(method, "method must not be null");
        Objects.requireNonNull(path, "path must not be null");
        Objects.requireNonNull(allocator, "allocator must not be null");
    }
}

// Functional registry: resolve encoder by payload type.
@FunctionalInterface
public interface HttpRequestBodyEncoderRegistry {
    HttpRequestBodyEncoder resolve(Class<?> payloadType);
    static HttpRequestBodyEncoderRegistry empty() { return type -> null; }
    // Highest-priority match resolver over the given encoders (see priority-ordering clause in §3).
    static HttpRequestBodyEncoderRegistry of(List<HttpRequestBodyEncoder> encoders) { /* … */ }
}

// Response decoder — wire body → typed payload.
public interface HttpResponseBodyDecoder {
    boolean supports(Class<?> targetType, String contentType);
    Object decode(LoanedBuffer body, Class<?> targetType, HttpResponseDecodingContext context);
    default int priority() { return 0; }
}

// Response decoding context: status + headers + allocator.
public record HttpResponseDecodingContext(
        int status,
        List<HttpHeader> headers,
        MemoryAllocator allocator
) {
    public HttpResponseDecodingContext {
        Objects.requireNonNull(headers, "headers must not be null");
        Objects.requireNonNull(allocator, "allocator must not be null");
    }
}

// Functional registry: resolve decoder by target type + content type.
@FunctionalInterface
public interface HttpResponseBodyDecoderRegistry {
    HttpResponseBodyDecoder resolve(Class<?> targetType, String contentType);
    static HttpResponseBodyDecoderRegistry empty() { return (type, ct) -> null; }
    // Highest-priority match resolver over the given decoders (see priority-ordering clause in §3).
    static HttpResponseBodyDecoderRegistry of(List<HttpResponseBodyDecoder> decoders) { /* … */ }
}
```

`HttpEncodedBody` (`{ List<HttpHeader> headers, LoanedBuffer body }`, since 0.5.0) is **reused** as the wire carrier for both request and response paths. It is already the established off-heap encoded-body shape for the server side; duplicating it for clients would add a parallel type with no semantic difference.

### 2. Provider slots (new, in `HttpKernelProviders`)

Two new `ScopedValue` slots bound during HTTP bootstrap analogous to `HTTP_CLIENT_ENGINE`:

```java
public static final ScopedValue<HttpRequestBodyEncoderRegistry>  HTTP_REQUEST_BODY_ENCODER_REGISTRY  = ScopedValue.newInstance();
public static final ScopedValue<HttpResponseBodyDecoderRegistry> HTTP_RESPONSE_BODY_DECODER_REGISTRY = ScopedValue.newInstance();

public static Optional<HttpRequestBodyEncoderRegistry>  httpRequestBodyEncoderRegistry()  { /* isBound? get : empty */ }
public static Optional<HttpResponseBodyDecoderRegistry> httpResponseBodyDecoderRegistry() { /* isBound? get : empty */ }
```

Both slots are optional (applications without typed body codecs should still bootstrap HTTP). Accessor methods follow the existing optional-slot pattern from `HttpKernelProviders.httpClientEngine()` — i.e., `Optional<HttpRequestBodyEncoderRegistry> httpRequestBodyEncoderRegistry()` and `Optional<HttpResponseBodyDecoderRegistry> httpResponseBodyDecoderRegistry()`. Provider-discovery via `HttpProvider` (extension of the existing `responseBodyEncoderRegistry()` accessor) is the canonical bootstrap source; the `ScopedValue` slots are the read path. Clients that do not need typed binding (raw `HttpClientEngine.send` callers) do not require these slots to be bound.

### 3. Community driver (Jackson 3)

Two independent classes in `exeris-kernel-community`, package `eu.exeris.kernel.community.http` — one per direction. Each is a single SPI implementation; registries are composed at application bootstrap via static factories on the registry interfaces (see below):

```java
package eu.exeris.kernel.community.http;

public final class CommunityJsonRequestBodyEncoder implements HttpRequestBodyEncoder {
    public CommunityJsonRequestBodyEncoder(ObjectMapper mapper);
    // supports(Class)        : non-null → eligible (Jackson handles any JSON-mappable type).
    // encode(...)             : mapper.writeValueAsBytes → LoanedBuffer; emits content-type + content-length
    //                           via HttpEncodedBody.headers().
}

public final class CommunityJsonResponseBodyDecoder implements HttpResponseBodyDecoder {
    public CommunityJsonResponseBodyDecoder(ObjectMapper mapper);
    // supports(Class, String) : content-type matches application/json or application/*+json
    //                           (RFC 6838 §4.2.8); content-type null/empty tolerated per decoder contract.
    // decode(...)             : mapper.readValue; never closes the buffer (ownership is facade-side).
}
```

Registries are composed at the application boundary using static factories on the SPI registry interfaces:

```java
HttpRequestBodyEncoderRegistry  reqRegistry  =
        HttpRequestBodyEncoderRegistry.of(List.of(new CommunityJsonRequestBodyEncoder(mapper)));
HttpResponseBodyDecoderRegistry respRegistry =
        HttpResponseBodyDecoderRegistry.of(List.of(new CommunityJsonResponseBodyDecoder(mapper)));
```

Both `of(List<...>)` factories return a resolver that selects the highest-`priority()` candidate whose `supports(...)` reports `true`; see the registry priority-ordering contract clause below.

The two-class shape preserves composition flexibility — applications can mix bindings (e.g., Jackson encode + Protobuf decode, or Jackson encode + raw-bytes passthrough decode) without overriding a paired-lifecycle registry. The per-direction `Community*` class shape is consistent with the rest of the Community module (`CommunityHttpClientEngine`, `CommunityHttpProvider`, `CommunityKernelContextEnricher`, server-side `JsonBodyEncoder`) — each driver is a single SPI implementation.

The JSON family (`application/json` plus `application/*+json` variants per RFC 6838 §4.2.8) is subscribed by the decoder's `supports(Class, String)` predicate. Jackson 3 remains a Community-tier dependency; SPI types never see `ObjectMapper`. A future Enterprise driver (e.g., Panama-native JSON) can ship its own per-direction implementation behind the same SPI without touching SPI, Core, or the facade.

**Driver exception wrapping.** Drivers wrap binding-specific exceptions (e.g., `tools.jackson.core.JacksonException`) into a generic `RuntimeException` (`IllegalStateException` matches the server-side `JsonBodyEncoder.java:52` pattern) before crossing back to the SPI / Core boundary. No Jackson types appear in any public SPI or Core API surface; `KernelWebClient.WebClientException`'s `cause` chain is opaque `Throwable`.

**Registry priority-ordering contract** (applies to both `HttpRequestBodyEncoderRegistry` and `HttpResponseBodyDecoderRegistry` Javadoc):
> When multiple candidates report `supports(...) == true`, the resolver MUST return the candidate with the highest `priority()` value. Ties resolve by registration order (first-registered wins). Resolver returns `null` when no candidate supports the inputs — the façade maps this to `WebClientException` at call site.

**Decoder contract clauses** (`HttpResponseBodyDecoder.decode` Javadoc):
> Implementations MUST tolerate `contentType == null` or empty (server omitted the header) — registry resolution may return any decoder claiming support for `targetType` with `contentType` ignored. Implementations MAY return `null` when `body.size() == 0` and `targetType` is nullable; the façade (`KernelWebClient.execute`) decides whether `null` is acceptable per call (e.g., `Void.class` → null OK; any other type → `WebClientException` with status + empty body).

**Request encoder context-locking clause** (`HttpRequestBodyEncoder.encode` Javadoc):
> Implementations MUST NOT depend on request headers. The `HttpRequestEncodingContext` deliberately carries only `(method, path, allocator)` because the encoder runs before header finalization — the encoder's job is to produce body bytes plus the `content-type` it owns (returned in `HttpEncodedBody.headers()`). Headers established by the encoder are merged with façade-owned headers (`accept`, `content-length`) and enricher-added headers (per ADR-032) at the call site. This asymmetry vs server-side `HttpResponseEncodingContext.request()` is intentional — server response encoders run AFTER the request is fully parsed; client request encoders run BEFORE the request exists as a carrier.

**Decoder SPI surface rationale** (`HttpResponseBodyDecoder.decode` signature is generics-free):
> The decoder returns `Object` and accepts `Class<?>` rather than capturing `<T>`, mirroring the server-side `HttpResponseBodyEncoder.encode(Object payload, HttpResponseEncodingContext) → HttpEncodedBody`. Both SPI surfaces stay generics-free; the cast site lives in `KernelWebClient.execute` as a single `@SuppressWarnings("unchecked")` at the façade. A generics-free SPI surface eases alternative bindings (Jackson `TypeReference`, Protobuf descriptors) without forcing `<T>` propagation, and keeps the symmetric pattern principle intact — same shape on both sides of the wire.

The existing `JsonBodyEncoder` server-side class (since 0.5.0) is **kept as-is** in this ADR — refactoring server-side encoding to subscribe a content-type the same way the client decoder does is a v1.0 cleanup (see Alternative B), out of scope here.

### 4. `KernelWebClient` facade (new, in `exeris-kernel-core`)

The facade moves out of the Community tier into Core under `eu.exeris.kernel.core.http.client`, alongside the existing `core.http.{hpack, http1, http2, routing}` family established by ADR-009.

```java
package eu.exeris.kernel.core.http.client;

public final class KernelWebClient {

    // Five-argument primary constructor.
    public KernelWebClient(
            HttpClientEngine engine,
            MemoryAllocator allocator,
            HttpRequestBodyEncoderRegistry  requestEncoders,
            HttpResponseBodyDecoderRegistry responseDecoders,
            HttpClientRequestEnricher       enricher);                       // ADR-032

    // Four-argument convenience: enricher defaults to HttpClientRequestEnricher.noop().
    public KernelWebClient(
            HttpClientEngine engine,
            MemoryAllocator allocator,
            HttpRequestBodyEncoderRegistry  requestEncoders,
            HttpResponseBodyDecoderRegistry responseDecoders);

    public <T> T get(String path, Class<T> responseType);
    public <T> T post(String path, Object body, Class<T> responseType);
    public <T> T patch(String path, Object body, Class<T> responseType);
    public <T> T delete(String path, Class<T> responseType);

    public static final class WebClientException extends RuntimeException {
        public int    status();
        public String responseBody();
        public boolean isNotFound();
    }
}
```

The constructor **loses** the `ObjectMapper` parameter — Jackson descends to the codec driver. Core does not acquire a Jackson dependency. The facade reads only SPI types (`HttpClientEngine`, `MemoryAllocator`, `HttpRequestBodyEncoderRegistry`, `HttpResponseBodyDecoderRegistry`, `HttpClientRequestEnricher`).

Behaviour preserved verbatim from `CommunityWebClient` (ADR-026):

- 2xx → resolve decoder by `(responseType, response content-type)` → `decode` → return; `Void.class` returns `null`.
- 404 → `WebClientException` with `status() == 404` and `isNotFound() == true`.
- Other non-2xx → `WebClientException` with status + body.
- Every call blocks the caller's virtual thread through `HttpClientEngine.send`.
- Request body buffer: facade allocates via `MemoryAllocator`, hands ownership to engine on `send`. On encoder failure between allocate and engine-transfer the buffer is released locally.
- Response body buffer: returned by engine, decoded, closed in a `finally`. Callers never see the buffer.
- Enricher chain (ADR-032) runs after the base `HttpRequest` is constructed and before `engine.send`.

### 5. `CommunityWebClient` removal

`eu.exeris.kernel.community.http.client.CommunityWebClient` is **removed**. Pre-1.0 has no external SPI consumers (memory: `feedback_breaking_changes_terminology`, `project_kernel_context`) and the only known consumer of the FQN is the generator in `exeris-tooling`, which is updated in lockstep (item 7). Removal is preferred over deprecation because retaining a stale `Community*` facade after introducing the tier-neutral one would re-introduce the tier-identity leak in any new application that copy-pasted the old constructor signature from an example.

### 6. Integration test relocation

`CommunityWebClientIntegrationTest` is renamed to `KernelWebClientIntegrationTest` and lives at `exeris-kernel-community/src/test/java/eu/exeris/kernel/community/http/client/KernelWebClientIntegrationTest.java`. The test wires a real `CommunityHttpServerEngine` listener, constructs `CommunityJsonRequestBodyEncoder` and `CommunityJsonResponseBodyDecoder` from a real `ObjectMapper`, composes them via `HttpRequestBodyEncoderRegistry.of(...)` / `HttpResponseBodyDecoderRegistry.of(...)`, builds a `KernelWebClient` against `CommunityHttpClientEngine`, and exercises every public verb plus the documented error semantics. No external network dependency. Coverage matches the ADR-026 §TCK + binding list (2xx round-trip per verb, 4xx → `WebClientException`, 404 predicate, 5xx, null arg rejection, `Void.class` discard) plus one additional case for the request-body encoder seam: a `null` request body still produces a valid bodyless request without invoking the encoder registry.

Cross-tier note: the class under test (`KernelWebClient`) lives in Core, but the test physically resides in the Community module because `exeris-kernel-core/pom.xml` does not declare `exeris-kernel-community` on its test scope. Reversing that direction (Core → Community at test scope) would invert the SPI/Core/Community dependency direction defined by The Wall. The test class exercises Core's `KernelWebClient` from Community's test classpath where the in-process `CommunityHttpProvider`, `CommunityHttpClientEngine`, `CommunityHttpServerEngine`, and Jackson driver classes are already on the path.

### 8. Naming distinguo — `Community*` is for drivers, not facades

The `Community*` class-name prefix convention (memory: `feedback_community_class_naming`) is a **driver-side convention** for concrete SPI implementations shipped in `exeris-kernel-community`: `CommunityHttpProvider`, `CommunityHttpClientEngine`, `CommunityHttpServerEngine`, `CommunityTlsEngine`, `CommunityMemoryProvider`, `CommunityJsonRequestBodyEncoder` + `CommunityJsonResponseBodyDecoder` (this ADR), `CommunityKernelContextEnricher` (ADR-032), etc. These classes implement SPI contracts and are interchangeable with Enterprise alternatives.

Tier-neutral facades and orchestration classes in Core do not use the prefix. `KernelWebClient` is the canonical example introduced by this ADR — it composes any `HttpClientEngine` driver (Community today, Enterprise tomorrow) with any codec registry driver (Community Jackson today, Enterprise Panama JSON tomorrow). The Sprint 2/3 misstep with `ExerisWebClient` → `CommunityWebClient` (ADR-026 Amendment 2026-05-17) over-corrected toward driver-prefix conformance in a place where the facade-vs-driver distinguo applies. ADR-034 records the distinguo explicitly so future facades land in Core without re-litigating the prefix question.

## Alternatives Considered

### A) Layer the typed API on `HttpClientEngine` SPI directly

Add `<T> T sendJson(...)` / similar helper methods to `HttpClientEngine`. Rejected for the same reason ADR-026 §Alternatives A rejected it: forces every engine implementation to ship a binding library, breaking the SPI implementation-blind invariant. The body codec belongs above the wire SPI, not inside it.

### B) One shared `HttpBodyEncoder` / `HttpBodyDecoder` SPI for both server and client

Unify the server-side `HttpResponseBodyEncoder` (since 0.5.0) and the new client-side `HttpRequestBodyEncoder` into a single contract. Rejected for this ADR: the three encoding contexts (server-response `Accept` negotiation, client-request method + path, client-response status + headers) are materially different — collapsing them forces a context type with optional members on every codepath. The symmetric **pattern** is preserved (encoder + context + registry, mirrored on each side), the **types** are kept separate.

A v1.0 cleanup may revisit unification once two or more SPI types have been live for a release and a concrete simplification pressure has accumulated. The ADR-034 shape does not block that cleanup; it codifies the symmetric-pattern-with-separate-types stance for 0.8 → 0.x.

Relatedly, the Community driver is intentionally split per-direction rather than paired (cross-reference Alternative G) — keeping encoder and decoder as independent SPI implementations preserves the same composition flexibility on the driver side that the separate-types stance preserves on the SPI side.

### C) `KernelWebClient` in a new module `exeris-kernel-client`

Carve out a dedicated Maven module for the facade and its codec registry interfaces. Rejected — premature. Core already hosts the related `core.http.{hpack, http1, http2, routing}` family per ADR-009; `core.http.client` is a sibling subpackage with no new dependency edges. A new module adds CI cycles, a Maven Central artifact, module-info bookkeeping, and a separate release artefact for one public facade class. Promote later if the facade surface grows non-trivially.

### D) `KernelWebClient` in SPI

Place the facade in `exeris-kernel-spi` so it sits at the same tier as the contracts it composes. Rejected — the facade **consumes** SPI bindings (it resolves a `HttpRequestBodyEncoderRegistry` to do work). SPI hosts contracts, not orchestrations against those contracts. By the same rule that `HttpClientEngine` lives in SPI and `CommunityHttpClientEngine` lives in Community, the orchestration that drives them lives in Core.

### E) Deprecate `CommunityWebClient` for one release before removing

Mark `CommunityWebClient` as `@Deprecated(forRemoval = true, since = "0.8.0")`, ship `KernelWebClient` alongside it, remove in 0.9.0. Rejected — pre-1.0 (TRL-3), no external SPI consumers, no migration constituency outside the lockstep-updated generator. Carrying a second-tier facade that re-exports the tier-identity leak for a release cycle costs more (documentation, examples, generator-output ambiguity) than it saves. The lockstep removal is the cleaner shape for pre-1.0.

### F) Keep `CommunityWebClient` and add a tier-neutral `KernelWebClient` alongside it

Two facades, one tier-correct in Community and one tier-neutral in Core, with the generator pointing at the Core one and the Community one kept for backward source compatibility. Rejected — duplicates the maintenance surface (every constructor change, every header behaviour change, every error-mapping refinement applies in two places) for no consumer benefit. The generator is the only known consumer.

### G) Single Community class implementing both registries + both directions

Earlier draft of this ADR proposed one `CommunityJsonBodyCodecRegistry` class that implemented `HttpRequestBodyEncoderRegistry`, `HttpResponseBodyDecoderRegistry`, `HttpRequestBodyEncoder`, and `HttpResponseBodyDecoder` simultaneously — paired encoder + decoder + resolver in a single Jackson-bound class. Rejected (cross-referenced from Decision §3 and Alternative B) — the paired-lifecycle illusion prevents callers from mixing bindings per direction (e.g., Jackson encode + Protobuf decode, or Jackson encode + raw-bytes passthrough decode) without overriding the entire registry. The two-class shape (`CommunityJsonRequestBodyEncoder` + `CommunityJsonResponseBodyDecoder`) composed via `HttpRequestBodyEncoderRegistry.of(...)` / `HttpResponseBodyDecoderRegistry.of(...)` preserves composition flexibility and matches the per-direction `Community*` class convention used elsewhere in the module.

## Consequences

### Positive

- **Tier identity removed from the build-time surface.** `KernelClientGenerator` references `eu.exeris.kernel.core.http.client.KernelWebClient` — no `Community*` symbol leaks into application source files emitted by the tooling. Build-time analogue of The Wall (ADR-006) is preserved.
- **Symmetry with server-side body codec SPI.** `HttpRequestBodyEncoder` / `HttpRequestEncodingContext` / `HttpRequestBodyEncoderRegistry` mirror `HttpResponseBodyEncoder` / `HttpResponseEncodingContext` / `HttpResponseBodyEncoderRegistry` (since 0.5.0). Naming, shape, and `empty()` factory all align. Reviewers familiar with the server side can read the client side without ramp-up.
- **Jackson stops being a Core concern.** The facade depends on the codec SPI; Jackson 3 is a Community driver detail. Core's dependency surface shrinks (it never had Jackson, and this ADR keeps it that way under the new shape). Enterprise can ship an alternative driver (Panama-native JSON, CBOR, Protobuf) behind the same SPI.
- **Composition with ADR-032 preserved.** The 5-arg constructor wires `HttpClientRequestEnricher` exactly as ADR-032 documented for `CommunityWebClient`; the 4-arg convenience constructor defaults to `noop()`. No behaviour change for callers migrating from `CommunityWebClient` other than the constructor signature.
- **Extension point for future formats.** Any future `application/cbor`, `application/protobuf`, `application/x-msgpack` driver subscribes the same registry shape; no generator change, no facade change, no SPI change.
- **`Community*` naming convention sharpened.** ADR-034 §8 records the driver-vs-facade distinguo explicitly — future facades land in Core without re-litigating the prefix question.

### Negative / costs

- **One-time lockstep across four repos.** `exeris-docs` (slot reservation — already committed before this ADR), `exeris-kernel` (this PR — SPI + driver + facade + integration test + ADR + ADR-026 supersession marker), `exeris-tooling` (generator FQN swap + e2e fixture rename + Javadoc update + ADR-034 link stub), `exeris-kernel-enterprise` (one-line ADR-034 link stub). Coordination cost is the supersession's price.
- **Pre-amendment generator output does not compile against the new kernel artifact.** Any `*Client.java` emitted between ADR-026 (2026-05-16 / amended 2026-05-17) and ADR-034 (2026-05-19) imports `eu.exeris.kernel.community.http.client.CommunityWebClient`, which no longer exists. Pre-1.0, no external SPI consumers — blast radius bounded to in-flight feature branches inside `exeris-tooling` and any local fixture under `exeris-kernel` test sources. Re-running the generator against the new kernel artifact regenerates correct code.
- **Six new SPI types to TCK against.** The TCK surface grows by one driver-binding shape (Community Jackson registry); Abstract TCK bases for `HttpRequestBodyEncoder` and `HttpResponseBodyDecoder` mirror the existing `HttpResponseBodyEncoder` TCK pattern. Not a new pattern, but new lines of Abstract* and TCK-binding test code.
- **`CommunityWebClient` is removed without a deprecation window.** Source-level callers (today: zero outside the lockstep-updated generator) must update imports. Pre-1.0 with no external SPI consumers makes this acceptable; the alternative (Alternative E) was rejected on cost-benefit grounds.

### Neutral / open

- **v1.0 cleanup may unify the symmetric-pattern-with-separate-types stance (Alt B).** If two releases of operational experience surface a concrete simplification pressure, ADR-034 does not block a unification. The decision today is to keep the contexts distinct because their fields are materially different.
- **Default registry binding via `HttpKernelProviders.HTTP_REQUEST_BODY_ENCODER_REGISTRY` / `HTTP_RESPONSE_BODY_DECODER_REGISTRY`** is provider-discoverable but not auto-bound by `KernelWebClient`. Applications still construct the facade explicitly with their chosen registries. A future ADR may opt to read the `ScopedValue` slot when no registry is passed; deferred until a use case emerges.
- **Future `EnterpriseWebClient` is not introduced by this ADR.** Today there is one facade — `KernelWebClient` — and one driver pair (Community Jackson). Should Enterprise need a distinct facade for an HTTP/3-specific feature (e.g., 0-RTT, server push semantics that do not fit the verb shape), it can land alongside in `eu.exeris.kernel.enterprise.http.client.EnterpriseWebClient`. Today, Enterprise composes with the same `KernelWebClient` over its own `HttpClientEngine` driver.
- **Server-side resolver priority backfill (follow-up).** Server-side `HttpResponseBodyEncoderRegistry.resolve` (since 0.5.0) documents priority ordering in Javadoc but the current Community resolver wires a single hard-coded encoder and never exercises the ordering. Backfill of the server-side resolver to actually honour `priority()` is tracked as a separate follow-up ticket (out of ADR-034 scope; the symmetric fix lands when the second server-side encoder appears).
