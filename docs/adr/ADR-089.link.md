# ADR-089 — Capability Entitlement Enforcement and Runtime Execution Contract (link stub)

**Authoritative copy:** [`exeris-docs/adr/ADR-089-capability-entitlement-enforcement-and-runtime-contract.md`](https://github.com/exeris-systems/exeris-docs/blob/main/adr/ADR-089-capability-entitlement-enforcement-and-runtime-contract.md)

ADR-089 establishes capability entitlement enforcement and the runtime execution contract, governed by the *Build ≠ License* boundary: source code can be compiled and evaluated freely, but production execution requires a validated cryptographic entitlement.

## Why this stub exists

ADR-089 adds a contract gate to the kernel bootstrap: a `KernelBootstrap` step that runs before any subsystem is initialized, ahead of the FOUNDATION phase (ADR-089 amendment of 2026-10-06), so the contract is decided before off-heap memory is committed. It defines the typed, immutable `ExecutionContract` record and the 3-tier enforcement model (`HARD`, `SOFT`, `AUDIT`).

## What is adopted in exeris-kernel

- **Typed Runtime Contract in the SPI:** `ExecutionContract`, `WorkloadEnvelope`, `EnforcementLevel` and `ExecutionEnvironment` are in `eu.exeris.kernel.spi.contract`, and `ContractBreachException` in `eu.exeris.kernel.spi.exceptions.contract`. ADR-089 as accepted names `eu.exeris.kernel.core.contract`; its 2026-10-06 amendment records the move: `KernelProviders.EXECUTION_CONTRACT` is an SPI `ScopedValue`, and the SPI cannot depend on Core.
- **KernelProviders Slot:** `KernelProviders.EXECUTION_CONTRACT` exposes the active contract via `ScopedValue` throughout the runtime lifecycle.
- **Entitlement declaration:** an artifact whose production execution needs an entitlement registers an `eu.exeris.kernel.spi.contract.EntitlementRequirement` through `ServiceLoader`, naming the capabilities it needs. Community artifacts register none. A provider that cannot be loaded, throws, or declares `null`, nothing or a malformed capability id stops the boot with `EX-LIC-0008` in every environment; outside the production classes, a declared requirement with no manifest is reported as one `SOFT` warning.
- **Phase 0 Bootstrap Gate:** `eu.exeris.kernel.core.contract.ContractBootstrapStep` runs before the subsystem orchestrator is built, so before any memory is allocated or socket bound. The environment comes from the configuration key `environment` (default `development`), never from the kernel profile.
  - No manifest: the Community fallback, which authorizes every environment — unless the environment is a production class (`production`, `production-load-sim`, `dr-hot`) and a requirement is declared, which aborts the boot with `EX-LIC-0005`.
  - A manifest: verified in every environment; in a production class the contract must also authorize the environment and every required capability (`EX-LIC-0007`, `EX-LIC-0004` at `HARD`).
  - `KernelBootstrap.inspect()` initializes nothing, so it runs no gate and binds no contract.
- **Enforcement levels:** `HARD` throws `ContractBreachException` out of the boot; the kernel never exits the JVM. Below `HARD`, `ExecutionContract.assertCapability` / `assertEnvironment` return a `ContractViolation`, and `ContractViolationReporter` reports it: `SOFT` as a `WARNING` through `System.Logger` (standard error on the default backend) plus `ContractEnforcementEvent` (`eu.exeris.kernel.contract.Enforcement`), `AUDIT` as the event only. Phase 0 and a manifest inside its grace period report this way; each distinct violation is reported once per process, and the event exists only while a JFR recording with it enabled is running. Each gate decision is also recorded as `ContractResolvedEvent` (`eu.exeris.kernel.contract.Resolved`) with its duration. Metering of `authorizedInstances` and the workload envelope is not implemented.
- **TCK Contracts:** `AbstractExecutionContractTck` and `AbstractLicenseManifestCryptoTck` in `exeris-kernel-tck`.

## When to consult ADR-089

- Any changes to `ExecutionContract`, `ContractViolation`, `WorkloadEnvelope`, `EnforcementLevel`, `ExecutionEnvironment` or `EntitlementRequirement`.
- Modifications to the contract gate (`ContractBootstrapStep`) or its place in `KernelBootstrap`.
- Any modification to error codes `EX-LIC-0004`, `EX-LIC-0005`, `EX-LIC-0007` or `EX-LIC-0008`.
- Review of capability checks and entitlement verification across kernel and capability modules.
