# Exeris Kernel v0.13.2 — Release Notes

| | |
|:--|:--|
| **Artifacts** | **`eu.exeris:*:0.13.2`** |
| **Date** | 2026-11-18 |
| **Predecessor** | 0.13.1 |
| **Framing** | Pre-1.0 / TRL-3. A patch release on the 0.13 line that ships features. Per-surface semver policy: [`docs/stability-matrix.md`](../stability-matrix.md). |

> **Scope of these notes.** They describe behaviour published in this repository, taken from the
> `[0.13.2]` section of [`CHANGELOG.md`](../../CHANGELOG.md). 0.13.2 changes no SPI type, touches no
> main source in `exeris-kernel-spi` or `exeris-kernel-core`, and adds one `MIGRATION.md` section, for the Kafka engine's shutdown.

## Summary

0.13.2 is a patch release, and it ships features: three additions to the Community Kafka events
driver (`exeris-kernel-community-kafka`) and one configuration key in Community events.

- The Kafka clients take configuration of their own: client property files, a client id, the kind of
  thread the consumer loop runs on, and a shutdown bound.
- The consumer loop gains a manual-commit mode, at-least-once on consumption.
- The engine gains a raw record channel for topics whose records carry no Exeris header, with
  rebalance hooks.
- `event.durableLogEnabled=false` lets the `events` subsystem boot without `persistence`.

Every addition is opt-in. An application that uses none of them behaves as on 0.13.1, with one
exception: the Kafka engine's shutdown changed in its default mode too (see *Shutdown* below).

## Kafka: client configuration

| Key | Meaning |
|:--|:--|
| `events.kafka.producer-properties-file` | Path of a `.properties` file of Kafka producer properties, applied after the binding's own, so an entry wins over them. |
| `events.kafka.consumer-properties-file` | The same for the engine's consumer. `enable.auto.commit=false` here selects the manual-commit mode. |
| `events.kafka.client-id` | Kafka `client.id` for both clients. A `client.id` in a properties file wins over it. |
| `events.kafka.consumer-loop-thread` | `virtual` (the default) or `platform`, a daemon platform thread. |
| `events.kafka.close-timeout-ms` | The bound on each blocking step of an engine shutdown; 30000 by default. |

- **Keys the binding owns are refused.** `bootstrap.servers` and `transactional.id` in either file,
  `key.serializer` and `value.serializer` for the producer, `key.deserializer`, `value.deserializer`
  and `group.id` for the consumer. A refused key, a missing or unreadable file, a loop-thread value
  other than `virtual` or `platform`, and a close timeout that is not positive fail the engine's
  creation with `EX-EVENT-6004`.
- **The event-log scan consumer takes no overrides.** `KafkaEventLog`'s consumer keeps its own fixed
  properties, and takes no client id either.
- **The same settings exist on `KafkaEventConfig`** for code that builds the engine itself:
  `producerOverrides`, `consumerOverrides`, `clientId`, `loopThread` and `closeTimeout`, each with a
  `with…` copy method. `toString()` prints the override key names, not their values, which can hold
  credentials.
- **Native image.** A class that a supplied property selects by name (a compression codec, an
  assignor, a SASL handler, an interceptor, a metric reporter) is not in the kernel's reachability
  metadata and is unverified; registering it is the consumer's
  ([ADR-103 amendment 2026-11-17](../adr/ADR-103-native-image-opt-in-build.md#amendments)).

The six keys from earlier releases (`bootstrap-servers`, `group-id`, `topic-prefix`,
`require-all-acks`, `producer-linger-ms`, `consumer-poll-timeout-ms`) are unchanged; all eleven are
now listed in [`docs/subsystems/config.md`](../subsystems/config.md#kernel-configuration-reference).

## Kafka: manual commit and shutdown

| Key | Meaning |
|:--|:--|
| `enable.auto.commit` (in the consumer properties) | `false` selects the manual-commit mode. Anything else, or nothing, keeps the auto-commit default. |

- **Manual mode.** Each record is delivered with `publishAndAwait` on the consumer loop thread, so its
  handlers run one after another on that thread, and the loop calls `commitAsync()` after every
  non-empty batch whose records were all handled. Any failure ends the loop without committing the
  batch, so the batch is delivered again to the next consumer of the group. A clean stop flushes the
  producer and commits with `commitSync`.
- **At-least-once covers consumption only.** It does not cover the output a handler produces: a
  batch's commit can precede the broker's acknowledgement of sends its handlers made. A send that
  fails asynchronously is surfaced by ending the loop before its next commit, not by redelivery;
  batches committed before the failure was reported stay committed.
- **A record whose handler always fails stops its partition.** The loop ends, the partition moves to
  the next member of the group, and that member fails on the same record. There is no skip and no
  dead-letter topic, and the engine does not restart a loop that has ended.
- **Handlers on the loop thread hold up polling.** A batch whose handlers together run past the
  consumer's `max.poll.interval.ms` gets the consumer evicted from its group, and a handler that waits
  for an event the same loop would deliver deadlocks. The loop thread carries none of the kernel's
  `ScopedValue` bindings.
- **Failures are reported.** `KafkaEventEngine.loopFailure()` returns the first failure that ended the
  loop, and a listener registered with `onLoopFailure(...)` is called once with it.
  `EventEngineStats.failedTotal()` counts framed events whose handler failed in manual mode; it was
  always `0` before and stays `0` in auto mode. `KafkaEventEngine.commitFailedTotal()` counts the
  per-batch asynchronous commits the broker did not accept; such a failure does not end the loop.
- **Auto mode stays at-most-once.** It is the default and is unchanged apart from its shutdown.

**Shutdown changed in both modes.** `close()` no longer interrupts the consumer loop. The loop
finishes the handlers in flight, flushes the producer, commits (manual mode only) and closes the
consumer, and the producer is closed last; the commit and both closes are bounded by the close
timeout. A loop that has not finished in time is interrupted, and that interrupt is not reported as a
failure. `EventLoop.stop()` and `close()` can therefore wait up to twice the close timeout, plus one
poll timeout, plus one second (61.25 s with the defaults), where `stop()` interrupted the loop and
waited at most 5 s. `close()` is now terminal: `start()` after it throws `IllegalStateException`. It
also closes the producer of an engine that was never started.

Reference: [`docs/subsystems/events.md`](../subsystems/events.md#kafka-consumer-loop-commit-modes-shutdown-and-raw-records).

## Kafka: raw record channel

`KafkaEventEngine.records()` returns a `KafkaRecordChannel`, for topics whose records carry no Exeris
header. It exposes `kafka-clients` types and lives in the Kafka module, not in the SPI.

| Method | Meaning |
|:--|:--|
| `subscribe(topic, KafkaRecordHandler)` | One handler per topic, the topic taken literally. The handler receives the `ConsumerRecord` as delivered. |
| `rebalanceListener(ConsumerRebalanceListener)` | Partition assignment hooks, called on the loop thread; a listener set late gets the current assignment once. |
| `afterPoll(Runnable)` | A hook the loop runs on its own thread after every poll, empty ones included, after the batch's raw handlers and before its commit. |
| `send(ProducerRecord, Callback)` | Produces the record as given, through the engine's producer. |
| `sendFailedTotal()` | Raw sends that failed asynchronously, counted apart from the engine's statistics. |
| `partitionsFor(topic)` | The topic's partition count. |

- **It bypasses the `EventBus`**, and with it the Exeris wire header and the ADR-101 isolation scoping:
  a raw record is neither stamped nor scoped. Raw topics cannot collide with framed ones: the topic of
  a registered event type and the event-log topic are refused in both directions, and an event type
  whose topic is subscribed raw cannot be registered.
- **Raw handlers run on the consumer loop thread**, in offset order per partition and not across
  partitions, in both commit modes. A raw handler that throws ends the loop. In auto mode the failing
  batch is still committed, because the client commits consumed positions when the consumer closes:
  auto mode stays at-most-once for raw records.
- **The rebalance hooks observe state a partition owns.** They are not a coordination mechanism: the
  kernel commits nothing when partitions are revoked.
- **What a measurement through the channel measures.** The driver's consumer and producer loop and the
  kernel runtime around it, not `EventBus` fan-out.
- **Off unless used.** With no raw subscription the engine behaves as without the channel.

## Events: `event.durableLogEnabled`

| Key | Meaning |
|:--|:--|
| `event.durableLogEnabled` | `true` by default. `false` removes the `events` subsystem's dependency on `persistence` and leaves the JDBC durable event log (`EVENT_STREAM_APPENDER` / `EVENT_STREAM_READER`) unbound. |

- **A boot that selects `events` alone no longer boots persistence** when the key is `false`. Under
  `BootstrapSelector.all()` persistence still boots, but `events` then initializes before it and stops
  after it, and the durable-log slots stay unbound.
- **The key is read once**, when the Community subsystem set is built. A value other than `true` or
  `false` fails the `events` subsystem's `initialize()` with a `SubsystemException` naming the key.
- **The testkit's `EmbeddedKernelFixture`** selects `persistence` itself, so `persistenceEngine()`
  stays available whatever the key says.
- **The Kafka native-image smoke sample** sets the key to `false` and no longer configures a database.

Reference: [`docs/subsystems/bootstrap.md`](../subsystems/bootstrap.md#the-holy-order-of-initialization),
[`docs/subsystems/config.md`](../subsystems/config.md#kernel-configuration-reference).

## Compatibility and upgrade

- **Compatibility impact: one behavioural break in the Community Kafka driver; everything else is
  additive.** No SPI type changes. The SPI compatibility gate has nothing to report.
- **The Kafka engine's shutdown is the break.** `start()` after `close()` throws
  `IllegalStateException`, and `EventLoop.stop()` and `close()` wait for the consumer loop up to
  61.25 s with the defaults before they interrupt it, where `stop()` interrupted at once and waited
  at most 5 s. This is what the SPI already states: `EventEngine.close()` says no component obtained
  from the engine may be used after it returns, and `EventLoop.stop()` says it blocks until
  everything already queued has been processed, with no time bound. On 0.13.1 `close()` closed the
  producer, so an engine started again after it could consume but every publish failed. A caller
  that relied on `stop()` returning within 5 s, or on starting an engine again after `close()`, has
  to change; the steps are in [`MIGRATION.md`](../../MIGRATION.md).
- **Community API additions:** in `exeris-kernel-community-kafka`, the `KafkaEventConfig` components
  `producerOverrides`, `consumerOverrides`, `clientId`, `loopThread` and `closeTimeout`, the enum
  `KafkaEventConfig.LoopThread`, the constant `DEFAULT_CLOSE_TIMEOUT_MS` and the methods
  `withProducerOverrides`, `withConsumerOverrides`, `withClientId`, `withLoopThread` and
  `withCloseTimeout`; `KafkaEventEngine.records()`, `loopFailure()`, `onLoopFailure(Consumer<Throwable>)` and
  `commitFailedTotal()`;
  the interfaces `KafkaRecordChannel` and `KafkaRecordHandler`. The six-argument `KafkaEventConfig`
  constructor and `KafkaEventConfig.defaults(...)` stay, so source and binary compatibility hold, but a
  record pattern over `KafkaEventConfig` or reflection over its components sees eleven components.
- **TCK:** `AbstractKafkaEventEngineTck` gains a case, `loop().stop()` leaves the loop not running,
  idempotently, with `stats()` agreeing. A binding of the suite outside this repository runs it.
- **Managed versions:** `exeris-kernel-bom` now manages `kafka-clients` 4.4.0 (was 4.3.1), Jackson
  3.3.0, Agrona 2.7.1, `lz4-java` 1.14.1, Logback 1.6.7, Bouncy Castle 1.87 and the PostgreSQL driver
  42.7.14. A build that imports the BOM gets them; one that pins its own versions is not affected.
  Flyway and Jedis are not moved, because their newer versions are new majors.
- **Upgrading from 0.13.1** is a version change. A Kafka deployment that sets none of the new keys sees
  one difference, the shutdown above: `close()` and `EventLoop.stop()` may take longer, up to about
  61 s with the defaults, and an engine cannot be started again after `close()`.

## Known limitations and not covered

- These are features in a patch release. They follow the 0.13 line's per-surface policy; the Kafka
  module is a Community artifact, not a declared SPI surface.
- At-least-once covers consumption, not handler output. Auto-commit mode stays at-most-once, and a raw
  handler failure in that mode still commits the batch.
- No skip, retry or dead-letter topic for a record whose handler always fails, and no automatic restart
  of a consumer loop that has ended.
- The producer flush in the shutdown sequence is not bounded by the close timeout; the wait for the
  loop thread is what bounds it.
- Classes selected through supplied Kafka client properties are outside the kernel's native-image
  metadata and unverified.
- `docs/subsystems/events.md`, `docs/subsystems/config.md` and `docs/subsystems/bootstrap.md` gained
  the new keys and behaviour. A whole-page re-verification of any of them against the code is not part
  of this release, and their `last-verified` dates are unchanged.
