## The headline is a measurement, and it is the first of its kind

**Nothing in the SPI broke at compile or link time.** `v0.11.0 → v0.12.0` is the first transition since the stability matrix
was published in v0.9.0 for which japicmp suggests a **minor** bump rather than a major one: zero
binary-incompatible changes on `stable` surfaces, zero source-incompatible changes on them, and —
new this milestone — **zero on `preview` surfaces either**. Both preceding minors broke something on
`preview`, which the policy permits and which consumers still had to read about.

That is not a claim about restraint. It is `tools/spi-api-diff/spi-api-diff.sh` compiling both
revisions of `exeris-kernel-spi` straight from git and diffing them, recorded in
[`spi-api-history.md`](./spi-api-history.md). A milestone this large ending additive is worth stating
precisely because the surface grew: a duplex wire, a time seam, and fault attribution on every kernel
exception all arrived without moving anything that was already there. Stream resolution added two
`preview` types, `StreamRouteResolver` and `StreamMatch`; the event bus gained the default method
`EventBus.isBrokered()` and three `EventBusException` factories; all are additions. The figures are
the † measurement recorded in `spi-api-history.md`, taken on a release candidate with
`--old v0.11.0 --new HEAD`; that page regenerates the row from the tag at the cut, and where the two
disagree the tag is authoritative.

japicmp reads signatures, so the claim stops at compile and link time. Several contract changes are
Javadoc only, and no signature diff can see them: the TLS clause of `HttpClientEngine#send`, under
which a client that carries a request over TLS verifies its server; the request-body clause of the
same method, under which the caller of `send` keeps ownership of the body (ADR-034 Amendment A1);
the client engine that a provider which verifies server identity returns from
`KernelCryptoProvider#createTlsEngine`, which refuses its handshake;
`TransportConnection#remoteAddress()`, an IP address literal on both ends; and
`EventBus#publishAndAwait`, whose wait on handlers is scoped to a bus that is not brokered. Each is
listed under *Compatibility: observable behaviour changes*.

The second headline is that **the path to a published release now exists and is gated.** Before this
milestone the release workflow could not be run at all. It now signs, produces an SBOM per published
coordinate, attests build provenance, verifies reproducibility by building twice, and ties the
uploaded bytes to the gated ones by digest. v0.12.0 is the first release that path publishes to
Maven Central; the upload runs with `autoPublish=false`, so the portal's validation is reviewed
before the publication becomes permanent.

## This milestone ships two artifacts

They carry the **same kernel** — same SPI, same subsystems, same tests — and differ in one axis plus
the build that follows from it. The preview line takes the distributable line's fixes by
cherry-pick, so it can trail: two pre-release fixes are recorded as not yet carried there, the
OpenSSL error-queue fix ([#535](https://github.com/exeris-systems/exeris-kernel/issues/535)) and
stream resolution through the bound handler
([#536](https://github.com/exeris-systems/exeris-kernel/issues/536)).

| | `eu.exeris:*:0.12.0` | `eu.exeris.preview:*:0.12.0` |
|:--|:--|:--|
| **JDK** | **25 LTS** | newest available — JDK 28 today |
| **`--enable-preview`** | **not required, and not imposed on you** | required, by definition |
| **Structured concurrency** | `StructuredScope` — virtual threads + `ScopedValue`, both GA | `StructuredTaskScope` |
| **Class-file major** | 69 | 72 |
| **For** | anything published, and any deployment that does not control its JVM | JVM-controlled deployments, and early access to what the next LTS will carry |

Take the distributable line unless you have a reason not to. The preview line absorbs JDK API churn
ahead of the LTS it converges into; it is not the better artifact. It keeps no parallel release-notes
file by decision — see `PREVIEW-TRACK.md` on that branch.

**The preview-clean property is now end to end.** v0.11 removed `--enable-preview` from main sources
and left it in test scope; v0.12 removes it from the whole line, fixtures included. A
`StructuredTaskScope` import anywhere on the distributable line is now wrong rather than exempt, and
the CI gate reads bytecode — `minor_version` and class-file major on the published jars — rather than
grepping source.

## Licence: the kernel is now Apache License 2.0, unmodified

**This is a compatibility item for anyone who evaluated the licence.** Two things changed, and the
second is the larger one.

The published kernel previously carried Apache 2.0 **plus Commons Clause**, which is not an open
source licence. That restriction is gone; the open-core kernel is Apache 2.0.

More importantly, the Apache 2.0 text the repository shipped was a **paraphrase**, not the licence.
It was missing clauses — including §5's "Notwithstanding the above" sentence, which is precisely the
sentence a contributor licence agreement has to interact with. A paraphrase of a licence is not that
licence, whatever the header says. The text is now the unmodified original.

Two published coordinates also declared no licence at all in their POM; both now declare it.

## Security

- **The Community TLS client verifies the server it dials** (ADR-074 Amendment A1). Before this
  release it encrypted and checked nothing — no trust, no server name, no host — so any certificate
  was accepted. A client now verifies the certificate chain against its trust
  (`crypto.tls.client.trustFile`, else OpenSSL's default trust) and the certificate's subject
  alternative names against the host it dialled: a DNS host against DNS entries, sent as the server
  name indication; an IP literal against IP entries. The subject common name is never consulted and
  partial wildcards match nothing. A server that fails is refused with `TlsHandshakeException`
  (`EX-NET-2001`) carrying the `X509_V_*` code, before any request byte is sent. No setting keeps TLS
  and skips verification.
- **Where it holds.** Outbound TLS is armed where a crypto provider is bound when the client engine is
  built and `exeris.transport.tls` is not `false`. An engine built anywhere else dials plaintext, as
  before; every client transport now records which in the
  `eu.exeris.kernel.transport.TransportTlsClientPosture` JFR event and an INFO log line. The S3 blob
  client and the OIDC provider's JWKS fetch are the exceptions, below.
- **The S3 blob driver reaches an `https://` endpoint over verified TLS** (ADR-056 obligation 10, amended).
  An `https` endpoint was refused at construction; it is now verified like any TLS client above,
  against the endpoint host. An `http://` endpoint is plaintext even where a crypto provider is
  bound, where it took TLS from the provider bound where the store was built. An `https` store is
  never downgraded: without the Community crypto provider, or under `-Dexeris.transport.tls=false`,
  it is not created (`EX-NET-4004`).
- **The OIDC provider fetches its JWKS key set only from a server it authenticated** (ADR-012 §4).
  `CommunityOidcIdentityProvider.overJwksEndpoint` took an application-supplied `KernelWebClient`,
  so a client built outside the kernel's scope, or under `-Dexeris.transport.tls=false`, fetched the
  key set in plaintext, and an on-path attacker could substitute a key and sign tokens that
  authenticated. It now takes the JWKS URI and builds its own engine from the scheme, as the S3
  driver does: `https` is verified TLS against the URI's host or no provider (`EX-NET-4004`);
  `http` is plaintext by request. In 0.10.0 through 0.11.0 no JWKS fetch through a Community engine
  authenticated its server.
- **A failed TLS handshake no longer closes healthy connections on the same thread.** OpenSSL's
  per-thread error queue was never emptied, so on the 3.x line one failed handshake — a plaintext
  client on a TLS port is enough — made the next healthy connection on that reactor read as failed.
- **The `StorageBootstrapSelected` JFR event no longer records credentials.** It recorded
  `storage.blob.location` verbatim, so `https://key:secret@host` put the credentials in any
  recording of bootstrap; the userinfo of a `scheme://` location is now recorded as `<userinfo>`.
- **Dependencies carrying published advisories are bumped** in `exeris-kernel-bom`: Jackson 3.1.1 →
  3.2.2, the PostgreSQL driver 42.7.11 → 42.7.13, and lz4-java 1.10.2 → 1.11.2, which reaches the tree
  as a runtime transitive of `kafka-clients`.

## Compatibility: knobs that did nothing now do something

The first two items are configured values the runtime previously ignored; the other two are limits
that were compiled in, defaulted two ways, or borrowed from the other side of the process. If you had
set one, the behaviour you get after upgrading is the behaviour you asked for — which may differ from
the behaviour you observed.

- **`transport.idleTimeoutMillis` reclaims idle connections.** It had never done so. A deployment
  that set a short idle timeout and saw connections persist will now see them closed.
- **HTTP/2 enforces the header limits an operator configures.** They were honoured on HTTP/1 and
  silently ignored on h2. A request that exceeded a configured limit and was served over h2 will now
  be rejected.
- **The PAQS admission ceiling is settable** rather than compiled in
  (`transport.paqs.maxActiveStreams`, ADR-071 amendment), and the **connection cap has one default**
  instead of two disagreeing ones (ADR-081): `HttpConfig.DEFAULT_MAX_CONNECTIONS` moves from 1 000 to
  4 096, matching `transport.maxConnections`. The cap refuses cleanly only while it is reached before
  the process's descriptor limit, so check `ulimit -n` against it.
- **`http.maxResponseBodyBytes`** — the HTTP client stops borrowing the *server's* ingress limit to
  size its own reads. A client and a server in one process no longer share a limit that was only ever
  meant for one of them.

## Compatibility: observable behaviour changes

- **Outbound TLS is a decision, not a consequence.** A `CLIENT`-mode transport armed TLS whenever a
  crypto provider was bound, with no way to decline it. It dials TLS when `exeris.transport.tls`
  allows it — `-Dexeris.transport.tls=false` now declines it — and a crypto provider is bound where
  the client engine is built. The request does not decide: `HttpRequest` carries no scheme. The S3
  client and the JWKS fetch are the exceptions: their endpoint's scheme decides (next entries).
- **The S3 driver's transport follows its endpoint's scheme.** An `http://` endpoint is plaintext
  where a crypto provider is bound, where it dialled TLS; an `https://` endpoint is honoured, where
  it was refused. The signed `Host` and a presigned URL omit the scheme's default port, so an
  `http://host` endpoint with no port signs `Host: host` where it signed `host:80`, and its
  presigned URLs lose `:80`.
- **`CommunityOidcIdentityProvider.overJwksEndpoint` takes the JWKS URI**, not a `KernelWebClient`
  and a path, and the provider it returns is `AutoCloseable`: it owns the engine the key set is
  fetched with. An `https` URI is refused where the provider cannot verify the server; an `http` URI
  is plaintext wherever the provider is built.
- **An outbound TLS connection verifies its server** — see [Security](#security). A peer with a
  private-CA or self-signed certificate that was accepted before is refused now, until the client is
  told to trust it (upgrade step 8).
- **A `DUAL` transport dials out as a client.** Its outbound connections ran the server side of the
  handshake with the listener's certificate; they now dial as a verifying client (plaintext, as
  before, when the listener holds no certificate).
- **A kernel booted with `http.mode=DUAL` starts.** Its client engine was given a second `DUAL`
  transport — a listener on the server's port, with the server's certificate — that nothing gave a
  stream handler, so the `http` subsystem failed the boot. The client engine's transport is now a
  `CLIENT` one, whatever `HttpMode` says.
- **A Community client transport refuses to dial TLS through a crypto provider that cannot verify.**
  Where the bound crypto provider is not the Community one and `exeris.transport.tls` is not
  `false`, a `CLIENT` transport — and so every Community HTTP client engine whose `HttpConfig` is not
  `DISABLED`, other than the S3 blob client's for an `http://` endpoint and the JWKS fetch's for an
  `http://` URI — fails at construction with
  `TransportException` `EX-NET-4004`, and a `DUAL` transport whose listener holds certificate
  material fails each `connect` before any socket opens with
  `EX-NET-4001`, caused by `TlsHandshakeException` detail
  `bound crypto provider cannot verify an outbound peer`. Neither verified its server before. The
  posture event reports `REFUSED_FOREIGN_PROVIDER` (upgrade step 8).
- **A Community client engine from `createTlsEngine` refuses its handshake.** An engine the
  Community crypto provider builds from a client configuration names no server to verify, so its
  `beginHandshake` throws `TlsHandshakeException` (`EX-NET-2001`) instead of completing
  unauthenticated; it still binds, reports its phase and closes. `KernelCryptoProvider#createTlsEngine`
  states this for any provider that verifies server identity, Javadoc only (upgrade step 8).
- **`eu.exeris.kernel.tls.HandshakeFailure` carries `EX-NET-2001`, not `EX-NET-2002`.** `EX-NET-2002`
  is the crypto provider's bootstrap code; a failed handshake is what `TlsHandshakeException`
  (`EX-NET-2001`) reports, and the event now agrees with it, server side included. It also gains
  `verifyResult`, the `X509_V_*` code of a client that expected a peer (`-1` otherwise).
- **`HttpClientEngine#send` states what a TLS client verifies** (javadoc only; no signature moved). A
  provider's client that carries a request over TLS verifies the server against its trust and the
  effective authority's host before sending, and refuses with `TlsHandshakeException`.
  `AbstractHttpClientTlsPeerVerificationTck` judges it as a suite of its own, apart from
  `AbstractHttpClientEngineTck`, so a provider whose client does not verify yet is not turned red by
  upgrading the TCK.
- **The HTTP client no longer dials `http.bindHost` and `http.port`** (ADR-074). Those keys are the
  listener's address. A `CLIENT` or `DUAL` client sends each request to the peer the request names,
  else to `http.client.defaultAuthority`, and refuses it when neither is set — see upgrade step 3.
- **A Community client connection reports the address it reached.** `remoteAddress()` on a dialled
  connection returned the name it was dialled by, such as `localhost`; it now returns the IP address
  the channel connected to, as an accepted connection does and as `TransportConnection#remoteAddress()`
  now states for both ends (Javadoc only). Code that read the dialled name back from the connection
  keeps that name itself (upgrade step 4).
- **A public route that opens a persistence session with no tenant is recorded.** For every
  `permitAll()` request whose persistence session was opened for a context declaring no tenant, the
  dispatcher emits the JFR event `eu.exeris.kernel.security.UnscopedRequestSession` (`method`,
  `path`, `readOnly`), once per request. The event type is enabled by default, so any recording
  captures it. With no `HttpRoutePolicy` bound every route is `permitAll()`, so an application that
  declares no policy records one event for each request that reaches persistence without a
  tenant-bearing context — every request of a route that reads shared, tenant-less data, and every
  database-backed health probe. To stop a route being reported, declare it `authenticated()` under a
  bound policy, or bind a `STORAGE_CONTEXT` that carries a tenant around its handler; disabling the
  event type in the JFR settings hides it for every route. Nothing starts failing, and `LONG_RUNNING`
  and stream routes are not covered.
- **`HttpClientEngine#send` leaves the request body with its caller** (ADR-034 Amendment A1; Javadoc
  only). The caller keeps ownership of the body and releases it after `send` returns or throws; the
  engine reads it during `send` and neither closes nor retains it. `KernelWebClient` now does so after
  each attempt, before the retry policy is consulted: it had released no body, so a client posting
  under load ended in `MemoryExhaustedException`. Every in-tree engine already behaved this way; the
  client engine TCK now fails one that closes or retains the body.
- **A booted kernel's HTTP client reports its configured default peer.** The engine bound as
  `HTTP_CLIENT_ENGINE` answered `defaultAuthority()` with `null` even with
  `http.client.defaultAuthority` set, so an `HttpClientRequestEnricher` binding a credential's
  audience to the peer (ADR-040) saw no authority for an unaddressed request. It now answers from its
  configuration, before and after `start()`, and refuses a `null` request with
  `NullPointerException` in every lifecycle state.
- **An event-bus failure carries the code of what failed** (stability matrix, behavioural note).
  Every message-constructed `EventBusException` carried `EX-EVENT-6002`, the queue-overflow code, so
  a Kafka send failure, an interrupted enqueue and a failing handler all read as a full queue. A
  publish the bus did not accept is `EX-EVENT-6009`, handlers that threw under `publishAndAwait` are
  `EX-EVENT-6010`, a rejected subscription is `EX-EVENT-6011`, and the two message constructors set
  `EX-EVENT-6001`; only queue overflow carries `EX-EVENT-6002` (upgrade step 10).
- **`EventBus#publishAndAwait` on the Kafka bus awaits the broker, and says so.** It returns once the
  broker acknowledges the record, while local handlers run later on the consumer loop; it never
  waited for a handler. The SPI now scopes the wait on handlers and `EX-EVENT-6010` to a bus that is
  not brokered, `EventBus.isBrokered()` (default `false`) says which kind a bus is, and the Kafka bus
  returns `true`. In-process buses are unaffected.
- **A WebSocket handler's `receive()` returns `null` at the peer's close frame.** It returned only
  once the peer dropped the TCP connection, so a client following RFC 6455 §7.1.1 — which has the
  server drop it first — held the handler's virtual thread and the connection until its own timeout.
- **A diagnostics call is audited when it is made, including one that throws** (ADR-033 obligation
  8). Each `CommunityKernelDiagnostics` method now emits its `EX-DIAG` JFR audit event as its first
  statement; a call that threw left no record before.
- **Transport fixes an operator can observe.** A write queued by one producer while another's flush
  empties the stream is written rather than stranded until the idle reaper resets the stream.
  Closing a connection the peer already closed now closes its stream, socket and selection key
  rather than leaving them to the idle reaper. A `connect` that races `stop()` or `close()` fails
  with `IllegalStateException` (`Engine is not running`) and leaves no socket, TLS engine or stream
  open. A failed TLS handshake reaches the caller as `TlsHandshakeException` (`EX-NET-2001`) on every
  later `read` or `write` instead of `stream closed` or end-of-stream, and bytes a TLS peer sent
  before closing stay readable, where an HTTP client could fail with `EX-NET-4002` on a complete
  response.
- **An HTTP handler can resolve `KernelProviders.MEMORY_ALLOCATOR`.** It is bound on the request and
  stream scope; before, resolving it inside a handler threw `NoSuchElementException`. A per-request
  allocator binding an application added to work around that can be removed.
- **A malformed HTTP request body answers `400`, not `500`** (ADR-036 amendment). Bad bytes are the
  caller's fault; an unresolvable codec is ours, and the two had shared one exception type.
- **A route can declare that it blocks** (ADR-077), and stops pinning a pooled connection for the
  duration.
- **A route authorization policy may decline to answer** (ADR-061 A2), so two authors can share a URL
  space without one silently owning it.
- **A `401` names its reason to the recording, not to the caller.**
- **`RowCursor.getString` states what it renders and refuses what it cannot** (ADR-080), over the
  column types that were actually measured rather than the ones assumed.
- **The RLS policy the kernel publishes is the one it tests.** They had diverged.
- **The storage subsystem boots**, and the operator names the driver.
- **The two PostgreSQL session keys the RLS contract rests on are now constants**
  (`ConnectionInterceptor.SESSION_KEY_TENANT_ID`, `SESSION_KEY_SHARED_SCOPE`). This matters most to
  anything that *generates* SQL, and the two keys did not start from the same place. Measured on the
  `v0.11.0` tag: `exeris.tenant_id` was already spelled across SPI, Core, TCK and Community, so a
  generator naming it was at least agreeing with the published surface. `exeris.shared_scope` appeared
  **only in Community** — zero SPI, zero Core, zero TCK. A tool emitting a shared-scope RLS policy
  against a 0.11 kernel was therefore transcribing a string that no published contract defined; it
  worked because a Community driver happened to set it, and nothing promised it would keep doing so.
  The failure mode if the two spellings ever drifted is the worst available — zero rows read, every
  write refused, and nothing pointing at the five characters responsible.

  Note what this does **not** claim: publishing the constant does not make the accessor and the
  variable name the same contract. `StorageContext.sharedScopeKey()` existed at 0.11 and still does;
  it is what an application reads. The session-variable name is what emitted SQL writes, and only from
  0.12 is it something a generator can reference rather than retype.

- **Every published jar declares its own JPMS module name**, before Central makes the naming
  permanent. Consumers on the module path get a stable name instead of an automatic one derived from
  the file.
- **`exeris-kernel-tck` publishes its contract as its main artifact** instead of hiding it under a
  classifier.

## Added

- **A duplex wire (ADR-084)** — the WebSocket SPI and its contract tests, the RFC 6455 frame codec in
  Core, the Community binding, and a `websocket` subsystem so an application that boots the kernel
  reaches an endpoint without naming a driver class. Two entry paths by design: an embedded engine
  with no kernel boot, for a tool that must not pay for a runtime; and the bootstrap-wired subsystem
  for an application. **Off unless asked for** — `websocket.enabled` defaults to `false`, so
  upgrading does not open a listener, and `websocket.allowedOrigins` defaults to empty, which accepts
  no browser origin.
- **`TimeSource` (ADR-082)** — time the kernel decides on goes through a seam, bootstrap-constructed
  and `ScopedValue`-threaded, with a live `Clock` view. Deterministic tests stop depending on the
  wall clock.
- **A kernel exception says whose fault it is (ADR-083)** — fault attribution on the exception rather
  than inferred from the error code by each caller.
- **A schema history ledger (ADR-073)** — apply-once is the runner's property, not something each
  migration's SQL has to arrange for itself.
- **A real-runtime test fixture for events and flow** in the testkit — one embedded kernel rather than
  a fixture per subsystem — plus a boot fixture that finally sends a request with a body through it.
- **`KernelWebClient.withAuthority(String)`** and a typed client that can read a collection; a
  request names its own peer (ADR-074), so a client stops dialling the address its own server listens
  on.
- **`FlowDefinitionBuilder.version(int)`** — the version ADR-064 made load-bearing is now settable
  where definitions are built.
- **`TransportStats.acceptFaults`** — a connection accepted and then failed during setup is counted,
  apart from `totalRejected`. Separately, a listener that ran out of file descriptors used to stay
  down; it now pauses and retries, recording each retry on the
  `eu.exeris.kernel.transport.CommunityAcceptRetry` JFR event.
- **`StreamRouteResolver` (ADR-043 Amendment A1)** — the SPI contract, `preview`, in
  `eu.exeris.kernel.spi.http`, through which a driver resolves stream routes on the bound handler,
  held by `AbstractStreamRouteResolverTck`. `HttpRouter` implements it, and a handler that wraps a
  router implements it by delegating, so a stream route behind a forwarder or a wrapper that does so
  is matched over HTTP/1.1. Before, the Community driver matched stream routes only when the router
  itself was bound. No handler bound today is served differently: an `HttpRouter` bound directly
  resolved its stream routes before, and a handler that does not implement the interface is still
  served respond-once. A generated application needs a tooling release built on kernel 0.12 (see
  *Carry-over*).

## Performance: the HTTP/1 read path stopped paying twice

Research first (`RFC-2026-09-01`), then a sweep. The read path was measured allocating roughly **20x
a request's wire size**; the causes were separable and were removed one at a time.

The figures in this section are exact allocation counts from in-repository measurements, not
benchmark results, and none comes from `exeris-benchmarks/results/reports/`: figure state
`unartifacted`. The header figures are recorded in
[`RESEARCH-2026-09-01-http1-header-allocation.md`](../research/RESEARCH-2026-09-01-http1-header-allocation.md),
the response figures in [`ROADMAP.md`](../ROADMAP.md) under the `http.maxResponseBodyBytes` entry.

- **Headers are parsed once, not twice.** `Http1Codec.parseHeaders` ran for connection state and h2c
  detection, then ran again to build the header list, materialising every name and value twice, then
  copied the finished list a third time. It now takes an optional visitor, so both come off one
  traversal. Exact per-thread bytes on a 16-header request: **9 848 B → 5 472 B, a 44% reduction**,
  of which the collapsed parse is 41% and the dropped copy the rest. Header order, values, bounds and
  the `-1` incomplete signal are unchanged.
- **Known field names resolve from a table** instead of being materialised per request.
- **The client stops decoding every response header twice.**
- **The router stops splitting the request path.**
- **A response costs what the response is, not what the ceiling allows.** The client sized every read
  against the configured maximum instead of against the body it was actually given. Measured on
  `MemoryStats.peakAllocatedBytes()`, one exchange on a fresh allocator under a 10 MiB ceiling: a
  `HEAD` response *declaring* a 10 MiB body and carrying none — the case that names the defect — cost
  **10 493 952 bytes before and 8 192 after**; a 200-byte `GET` went from **10 494 152 to 8 392**, and
  a 100 KiB `GET` from **10 596 352 to 204 843**. The overrun refusal is unchanged: a response past
  the ceiling is still refused, not truncated.
- **Outbound HTTP/1.1 connections are pooled and reused across requests.** `CommunityHttpClientEngine`
  keeps idle connections per authority and reuses the most recently released first. The pool holds
  at most `HttpConfig.maxConnections()` connections in total and at most that many, capped at 64, per
  authority, and drops a connection idle for `idleTimeoutMillis()` (`0` keeps it). A connection is
  returned for reuse only when the response is framed so that its end is known — an explicit
  `Content-Length`, or a bodyless `HEAD`, `204` or `304` — and never after a `1xx`, a
  `Transfer-Encoding`, an `Upgrade` or `Connection: close`. The engine retries nothing: a request
  that fails on a reused connection fails to its caller, and retrying stays the retry policy's
  decision (ADR-045). The pool reports acquisitions, releases and evictions on the JFR event
  `eu.exeris.kernel.community.http.HttpClientPool`.

## Quality and gate posture

- **The architecture guard now runs where it can see Core and Community.** Until this milestone the
  repository-wide ArchUnit rules lived in `exeris-kernel-tck`, whose classpath reaches the SPI alone,
  so they named the whole repository and inspected only the SPI: a `ThreadLocal` in Core left them
  green. `KernelTierDirectionArchitectureTest` and `KernelTierBanArchitectureTest` now run in
  `exeris-kernel-community`, the first module with all three tiers on one classpath, and each
  **asserts a non-zero class count for every tier** rather than passing vacuously. The SPI suite is
  scoped and named for what it can see.
- **SonarCloud analysis runs through the Maven scanner.** The standalone CLI scanner it replaces was
  handed a classpath glob that could not reach the local Maven repository; it matched 9 reactor jars
  and none of the 71 dependency jars on a module's real test classpath. *SonarCloud Code Analysis* is
  a required status check.
- **Tests that had never run, now run.** Four carrier-level TLS tests reported success by skipping, in
  every build, because their fixture directory was created by no script and no workflow; two more
  suites were recovered separately. A graph churn TCK was measuring a sampler draw rather than a byte
  ratio.
- **The memory subsystem was never stopped.** It reported the `Subsystem.isRunning()` default
  `false`, which tells the orchestrator there is nothing to shut down, so the one call that releases
  the kernel's memory allocator had never run in any process. It reports properly now and the
  allocator is closed at shutdown, which ends the validity of any segment still loaned out; memory
  is a foundation subsystem, so it stops last. The lifecycle TCK gained the companion assertion —
  `isRunning()` after `start()` — whose absence its own javadoc had recorded.
- **A carrier-pinning fence stopped counting a cold JVM, and the runtime stopped giving it one to
  count.** A transport engine left its JFR event classes to initialise at their first emit —
  `StreamLifecycleEvent` at the first stream completion, on a virtual thread, which cannot unmount
  while a `<clinit>` is on its stack, with every other virtual thread reaching that class pinned
  behind it. Invisible where carriers are plentiful; 15–16 ms per pin on a loaded host (recorded in
  `docs/subsystems/transport.md`) and past the 20 ms fence on a constrained one; figure state
  `unartifacted`. Every JFR event class in Core and Community is now classified in
  `CoreJfrEventCatalogue` or `CommunityJfrEventCatalogue`, warmed or
  deliberately cold, and the warmed ones are initialised on the thread that starts their subsystem;
  `JfrEventCatalogueCoverageTest` fails the build on an unclassified class. Every carrier-pinning
  fence, through `JfrPinningMonitor`, now sets class-loading and class-initialisation pins aside
  while still reporting them, unless a frame such as a native-library load or an FFM downcall shows
  the carrier was really blocked (upgrade step 4). The client-ingress regression test warms its path
  before recording and keeps its recording when it fails instead of deleting the evidence it was
  about to report on.
- **Supply chain**: reproducible jars, a CycloneDX SBOM per published coordinate, GPG signing, SLSA
  provenance attestation, and a readiness gate that fails on an SBOM that is present and wrong.
- **One gate was red at the cut and is recorded rather than quietly re-run.** The persistence
  RLS/interceptor gate failed on the milestone's final commit with `status code: 429, reason
  phrase: Too Many Requests` resolving `cyclonedx-maven-plugin` from Maven Central — a repository
  rate limit during plugin resolution, before any test ran. Re-run on the same commit: green, as
  was every other sequenced gate (Kafka, recovery continuity, transport stress, TLS on OpenSSL
  3.5.6 and 4.0.0). Noted because "we re-ran it and it passed" is worth nothing without saying
  what failed and why.
- **The diagnostics CLI runs what it ships.** Its shaded jar was executed nowhere in CI and died on
  its first command.
- **The documentation standards now run on every pull request, and three of them gate the release
  line.** `guardrails.yml` calls reusable workflows from `exeris-systems/.github`: frontmatter and
  registry checks (`docs-lint`, in `ramp` mode), commit format, pull-request body, and the one review
  of ADR-085 §J.33, which this repository no longer runs a workflow of its own for (ADR-087 §A.3) and
  which publishes a `docs-review / publish / verdict` check; a fifth, `judge-review`, runs when a
  pull request closes and gates nothing. The Javadoc gate of §F.21 runs from its own workflow,
  `javadoc.yml`. Before this milestone none of them ran at all, so a standard could be contradicted
  with nothing to say so. At the release (repository rulesets as read on 2026-09-30), the
  `development/0.12.0` ruleset requires `docs / docs-lint`, `javadoc / javadoc-gate` and
  `docs-review / publish / verdict` beside *Build & TCK Verification*, *SPI Compatibility Gate*,
  *SonarCloud Code Analysis* and the sequenced integration and TLS gates, so a red one blocks a merge
  there. The commit-format and pull-request-body checks are reported only. On `main`,
  `docs-review / publish / verdict` is the one guardrail the ruleset requires.
- **The agent layer is vendor-neutral, and has a runtime layer beneath it.** Nothing a consumer of
  the jars sees; recorded because it changes how a contributor's session is gated. Role profiles
  declare capabilities rather than one runtime's tool names, and the shared half is imported from a
  pinned, digest-verified bundle rather than copied. The four L0 hooks divide the work rather than
  each doing all of it: one **denies** an action no policy permits, one **blocks** a session from
  reporting itself finished while an owed check has not run, and two **record** the state that
  blocking hook reads.
- **The Javadoc gate arrives green, and that is the second-best outcome.** It was written to land
  red, on the argument that a gate is a worklist and a worklist nobody can see is one nobody clears.
  The list was cleared first — see *Documentation* below — so what the gate does now is keep it
  empty rather than show it. It is a required check on the `development/0.12.0` ruleset and a
  reported one on `main`.

## Upgrade notes (v0.11.0 → v0.12.0)

1. **Re-read your transport and HTTP configuration.** Nothing changed shape, but limits the runtime
   ignored, compiled in or borrowed are now enforced as configured — see "knobs that did nothing"
   above — and the HTTP connection cap
   defaults to 4 096, so check `ulimit -n` against it. For a deployment that makes no outbound HTTP
   calls, this is the section most likely to change what it does; for one that does, step 3 is at
   least as likely to.
2. **Nothing to recompile at the SPI.** No SPI signature moved; code that uses only the SPI needs no
   recompilation. Step 7 is a Core change that does, and step 4 lists a testkit interface that
   gained a method. Two runtime defaults did move — the HTTP client's destination, step 3, and TLS
   server verification, step 8.
3. **If the deployment makes outbound HTTP calls, name the peer.** `http.bindHost` and `http.port`
   are listen addresses only, and the HTTP client no longer reads them. At v0.11.0 a `CLIENT`
   client dialled `http.bindHost:http.port`, so a deployment reached its peer through those keys
   when it pointed them at a remote peer, or when it left them unset and their defaults — `0.0.0.0`
   for the host, and `network.port`, else `8080`, for the port — reached a listener on the same host.
   A booted `DUAL` kernel did not start at v0.11.0, so a `DUAL` deployment has no earlier peer to
   carry over; it names one the same way. Each of those now needs one of:
   - `http.client.defaultAuthority=host:port` — the port is required, an IPv6 address is bracketed
     (`[::1]:8443`), and a value carrying a scheme or a path is refused at startup; or
   - an address on each request: `KernelWebClient.withAuthority(String)` or
     `HttpRequest.withAuthority(String)`.

   A peer reached over TLS is verified against the host named here, so its certificate must carry
   that host in a subject alternative name — a DNS entry for a name, an IP entry for an address
   (step 8).

   Code that builds `HttpConfig` itself through the ten-argument constructor gets no default peer,
   and `HttpConfig` has no `with…` method for one: move to a constructor that takes
   `defaultAuthority` — the fourteen-argument one, or the canonical constructor. **If this step is
   missed**, the kernel still boots cleanly and with no warning; the first request that names no
   peer throws `IllegalStateException` naming `http.client.defaultAuthority`.
4. **If you consume `exeris-kernel-tck`**, drop the classifier — the contract is the main artifact.
   Peer addressing (ADR-074) also adds cases a binding that passed the 0.11 suite can fail:
   - `AbstractHttpClientEngineTck`: a started engine's `defaultAuthority()` reports the configured
     `HttpConfig#defaultAuthority()`, and `null` when none is configured; an engine that wraps
     another must report it too. The engine refuses with `IllegalStateException` a request naming
     no authority when it has no default, and a request whose authority carries no port.
   - `AbstractHttpProviderLoopbackTck`: a request naming an authority reaches that peer rather than
     the configured default. A request carrying no `Host` of its own reaches the server with exactly
     one, equal to its effective authority: the authority it names, or the configured default when
     it names none. The `Host` cases address the server through the new hook `loopbackHostName()`
     (default `localhost`), which must resolve to `loopbackHost()`. The `clientConfig` fixture names
     the peer only as its `defaultAuthority`, with no `bindHost` and the `-1` port, so a client that
     dials `bindHost` and `port` fails every unaddressed case; an override of `clientConfig` must
     name the peer the same way.
   - `AbstractTransportConnectionTck`: `remoteAddress()` is an IP address literal on both ends,
     including a client end dialled by host name — the contract the
     `TransportConnection#remoteAddress()` Javadoc now states, with no signature change. Where the
     transport dials by name, `createConnectionPair` should open the client end that way; against an
     address literal the case cannot tell a name from an address. The Community transport now meets
     it on the dialled end — see "A Community client connection reports the address it reached"
     under *Compatibility: observable behaviour changes*.

   Later contract corrections add cases a binding that passed the 0.11 suite can fail, with no hook
   or signature changed unless stated:
   - `AbstractHttpClientEngineTck`: `send(null)` throws `NullPointerException` on an engine not yet
     started, and an engine that closes or retains the request body fails (ADR-034 Amendment A1).
   - `AbstractEventBusTck`: on a bus whose `isBrokered()` is `true` its five in-process cases are
     skipped through an assumption; every bus runs a new case in which the payload's `close()`
     calls equal one plus its `retain()` calls once `publishAndAwait` returns.
   - `AbstractWebSocketExchangeTck.Close#receiveEndsOnClose` waits for the handler's `receive()` to
     return `null`, so a binding whose `receive()` stays blocked after the peer's close frame fails.
   - `TransportCarrierPinningTck` fails in setup a binding whose `createWritableStream()` returns a
     stream an earlier slot already holds.
   - `JfrPinningMonitor.Result`: `pinnedEvents()`, `pinnedCount()` and `hasPinning()` answer only
     for counted pins; class-loading and class-initialisation pins move to `classInitEvents()`. The
     earlier meaning is the two together. The records keep their constructors, so a binding still
     compiles and links; what changed is what the answer means.
   - `AbstractCryptoEngineTck`: the three Community-only checks are skipped, not passed, for a
     binding whose `isCommunityTier()` is `false`.

   **If you implement a testkit fixture interface**, `EmbeddedHttpEngineFixture` gained
   `runInKernelScope(Runnable)`, which a class outside the kernel adds.
5. **If you are on the module path**, module names are now declared rather than derived.
6. **WebSocket is opt-in.** Upgrading opens no socket; set `websocket.enabled` to change that, and
   set `websocket.allowedOrigins` before a browser can connect.
7. **If your code names `HttpRouter.StreamMatch` or calls `HttpRouter#resolveStream`, recompile it.**
   The record is now `eu.exeris.kernel.spi.http.StreamMatch` (SPI, preview), with the same
   components and the same `exact(HttpStreamHandler)` factory, and it refuses a `null` handler or
   parameter map at construction; import it from there in place of `HttpRouter.StreamMatch`. What
   changes is code naming the Core router's nested record or calling its method; the SPI side of the
   move is an addition, so step 2 holds. A handler you bind to
   `HTTP_SERVER_HANDLER` that wraps an `HttpRouter` and should serve its stream routes implements
   `StreamRouteResolver` by delegating to the router; one that does not is served respond-once, as
   before.
8. **TLS clients verify their server.**
   - A client that talks to a private-CA or self-signed server needs `crypto.tls.client.trustFile`
     naming the issuing CA — with its intermediates when the server's certificate is chained, since
     the Community server sends its leaf only — or, for a self-signed server, that certificate. A
     CA-issued server certificate alone in the file does not anchor its chain. The file replaces
     OpenSSL's default trust; `SSL_CERT_FILE` and `SSL_CERT_DIR` change only the default.
   - A client that talks to a plaintext peer declines TLS with `-Dexeris.transport.tls=false`. It is
     process-wide: every listener and client in the JVM declines together.
   - A deployment whose bound crypto provider is not the Community one cannot build a Community
     client transport that dials TLS. A `CLIENT` transport — the one a Community HTTP client engine
     builds, the S3 blob client's for an `https://` endpoint — fails at construction with
     `EX-NET-4004`, and a `DUAL` transport whose listener holds certificate material refuses each
     `connect` with `EX-NET-4001`, caused by `TlsHandshakeException` detail
     `bound crypto provider cannot verify an outbound peer`. A client that must dial TLS is built
     where the Community crypto provider is bound; a client of a plaintext peer declines TLS as
     above.
   - An S3 store with an `https://` endpoint needs the Community crypto provider bound where the
     store is built — in a booted kernel, the `crypto` subsystem in the same boot, since storage does
     not depend on it — and a trust that anchors the store's certificate chain: the store's issuing CA
     in `crypto.tls.client.trustFile`, or a public CA in OpenSSL's default trust. Its certificate
     must name the endpoint host in a subject alternative name — a DNS entry for a name, an IP entry
     for an address. Under `-Dexeris.transport.tls=false` an `https` store is refused with
     `EX-NET-4004`, never downgraded; booted, that refusal fails storage's `start()`, and so the
     boot. An `http://` endpoint needs no crypto provider and no trust, and is plaintext wherever
     the store is built.
   - An OIDC provider built by `overJwksEndpoint` is given the JWKS URI instead of a client and a
     path, and is closed with the application. For an `https` URI it needs the Community crypto
     provider bound where it is built and a trust that anchors the identity provider's chain; under
     `-Dexeris.transport.tls=false` it is refused with `EX-NET-4004`. An identity provider reachable
     only over plaintext is given an `http://` URI.
   - Code that calls the Community crypto provider's
     `createTlsEngine(CryptoProviderConfig.tcpClient())` and handshakes the engine now gets
     `TlsHandshakeException` from `beginHandshake`. Build a handshaking client engine with
     `CommunityKernelCryptoProvider#createClientTlsEngine`, which takes the trust and the expected
     peer.
   - A client of public HTTPS servers needs a non-empty default trust store, or a `trustFile` holding
     the public roots it should trust. An OpenSSL build or image whose default store is empty
     verifies no server; a chain sent without its root fails with `X509_V_*` code 20. The posture
     event reports the default file and directory in use, and the transport logs a WARNING when
     neither exists.
9. **A JFR rule keyed on `EX-NET-2002` for handshake failures now matches none.**
   `eu.exeris.kernel.tls.HandshakeFailure` carries `EX-NET-2001`; key the rule on that code, or on
   `verifyResult` to single out certificate verification.
10. **A filter keyed on `EX-EVENT-6002` now matches only queue overflow.** A publish the bus did not
    accept is `EX-EVENT-6009`, handlers that threw under `publishAndAwait` are `EX-EVENT-6010`, a
    rejected subscription is `EX-EVENT-6011`, and an `EventBusException` built through a message
    constructor carries `EX-EVENT-6001`. Code that relied on `publishAndAwait` to await handlers on
    the Kafka bus relied on something it never did: that bus awaits the broker, and
    `EventBus.isBrokered()` says so.
11. **If your code calls `HttpClientEngine#send` directly**, release the request body after `send`
    returns or throws; the engine does not. `KernelWebClient` does this for its own calls. An
    engine you implement reads the body during `send` and neither closes nor retains it.

## Carry-over to v0.13 / 1.0

The v0.7 through v0.10 notes carried this section and v0.11's dropped it, which left the next
milestone's planning to reconstruct its inputs from roadmap annotations. Restored here. Each linked
issue is open at the release, except #516, which is cited for the fix that left its item open.

**Lifecycle**

- **A `SIGTERM` stops the JVM without `shutdown()`**
  ([#542](https://github.com/exeris-systems/exeris-kernel/issues/542)). The kernel installs no signal
  handler or shutdown hook; `shutdown()` runs when `kernelMain` returns. In 0.12 turning a signal
  into an ordered shutdown is the host's job.
- **No initialisation deadline is enforced**
  ([#543](https://github.com/exeris-systems/exeris-kernel/issues/543)). `EX-BOOT-0003` is reserved,
  since no code raises it, and a subsystem whose `initialize()` blocks holds the boot indefinitely.
  Enforcing a deadline is later work.

**Events**

- **The Kafka bus awaiting its own handlers** — design work for a later version, left open by the
  fix for [#516](https://github.com/exeris-systems/exeris-kernel/issues/516), which scoped
  `publishAndAwait` to what a brokered bus can promise.
- **`KafkaPublishBus.publish` loses an asynchronous send failure**
  ([#544](https://github.com/exeris-systems/exeris-kernel/issues/544)).

**Transport and TLS**

- **A stream handler parked in `awaitReadableIngress` is not woken by its peer's close**
  ([#540](https://github.com/exeris-systems/exeris-kernel/issues/540)), so its teardown is delayed
  well past the close.
- **A writer is never parked, so a stream's outbound queue has no bound**
  ([#556](https://github.com/exeris-systems/exeris-kernel/issues/556)): a write the socket does not
  accept is queued for the reactor, and a peer that reads slower than the writer writes grows that queue
  and the off-heap buffers it holds.
- **Client TLS, beyond ADR-074 A1.** A `KernelWebClient` built with `CommunityHttpRetryPolicy`
  retries a verification failure ([#530](https://github.com/exeris-systems/exeris-kernel/issues/530)).
  The Community provider does not apply `CryptoProviderConfig#minimumTlsVersion`
  ([#531](https://github.com/exeris-systems/exeris-kernel/issues/531)). The Community server presents
  its leaf certificate only, not its chain
  ([#532](https://github.com/exeris-systems/exeris-kernel/issues/532)). Each verifying connection
  builds its own `SSL_CTX`. A client built outside the kernel's scope dials plaintext, unless its
  owner states the scheme as the S3 and JWKS clients do. No CRL or OCSP is consulted. The Enterprise
  client is outside the amendment and binds no peer-verification suite.
- **The preview line trails two pre-release fixes**: the OpenSSL error-queue fix
  ([#535](https://github.com/exeris-systems/exeris-kernel/issues/535)) and stream resolution through
  the bound handler ([#536](https://github.com/exeris-systems/exeris-kernel/issues/536)).

**TCK and test debt**

- **`AbstractGracefulShutdownTck` has no binding**, so its contract never runs
  ([#461](https://github.com/exeris-systems/exeris-kernel/issues/461)).
- **`AbstractFailurePolicyTck`'s three tests pass for hooks hardcoded to `true`**
  ([#462](https://github.com/exeris-systems/exeris-kernel/issues/462)).
- **The `highestPriorityWins()` tests recompute the ranking instead of invoking selection**, so they
  cannot fail ([#457](https://github.com/exeris-systems/exeris-kernel/issues/457)).
- **The stress gate's drain passes when the idle reaper discards a stranded write**
  ([#539](https://github.com/exeris-systems/exeris-kernel/issues/539)).
- **`immediateScheduleParkWakeOnSameContextIsRaceSafe` awaits one signal and asserts another**, and
  has failed once ([#519](https://github.com/exeris-systems/exeris-kernel/issues/519)).

**Graph**

- **`findShortestPath(source, target)` never searches, and the TCK cannot tell**
  ([#466](https://github.com/exeris-systems/exeris-kernel/issues/466)).
- **The SQL backend's `deleteNode` leaves every connected edge behind**
  ([#468](https://github.com/exeris-systems/exeris-kernel/issues/468)).
- **Heterogeneous multi-hop graph traversal** — moved *into* 1.0 scope during this milestone, and
  explicitly not into 0.12. The measurement behind the move: a 1-hop traversal returning one id
  spends ~11.7 KB of allocation on 16 bytes of payload (`GraphChurnRatioTck`, recorded in
  `docs/subsystems/graph.md`; figure state `unartifacted`), and client-side hop composition
  multiplies it. The RFC is unwritten.
- **A Graph testkit fixture**, deferred past the cut by decision, to sit beside the runtime fixture
  this milestone added for events and flow.

**HTTP and WebSocket**

- **WebSocket end-to-end coverage** — the subsystem's handler is not yet proven by opening a client
  connection over a socket, and nothing asserts the handshake handler reaching the engine over a real
  handshake. Both need a socket-level fixture.
- **`permessage-deflate`** — deferred, not rejected (ADR-084 §11). It is negotiated at the handshake
  and does not touch the handler surface, so it stays additive.
- **Stream routes, three known limitations.** Upgrading the kernel does not by itself make a
  generated application stream. One generated by a tooling release built against kernel 0.11 serves
  no stream route: its forwarder does not implement `StreamRouteResolver`, and its event-stream
  handlers read the event engine on a thread that carries no boot binding. Both are `exeris-tooling`
  changes, which need a tooling release built on kernel 0.12. HTTP/2 serves no stream route
  ([#534](https://github.com/exeris-systems/exeris-kernel/issues/534)), so a browser `EventSource`
  against TLS the kernel terminates, which negotiates `h2`, is served respond-once — terminate TLS
  upstream, or without TLS set `http.maxVersion=HTTP_1_1`; under TLS the ALPN selection does not
  honour `http.maxVersion` ([#533](https://github.com/exeris-systems/exeris-kernel/issues/533)). The
  Enterprise HTTP engine serves no stream route.

**Release, documentation and gates**

- **1.0 blockers**: the operational-limits sweep and the schema ledger closed this milestone, and the
  supply-chain gate exists and carries this release. The remaining register is
  [`1.0-scope.md`](./1.0-scope.md).
- **Documentation structure** — the fifteen older `subsystem` pages lack the `## Contract`,
  `## Hot path` and `## Failure modes` sections their type requires, tracked as
  [#547](https://github.com/exeris-systems/exeris-kernel/issues/547), and the frontmatter backfill is
  not finished. Both are measured once under *Documentation* above rather
  than restated here, and both are why CI still runs `ramp` and `--no-section-check`: a decision to
  keep "make it true" separate from "restructure it".
- **Bootstrap, events and telemetry Javadoc describe behaviour the code does not have**
  ([#545](https://github.com/exeris-systems/exeris-kernel/issues/545)); the verified subsystem pages
  are the reference until it is corrected.
- **Five modules are 0/0 but not gated whole** — Core and Community are checked on changed files
  only, and the testkit, the Kafka driver and the diagnostics CLI not at all; none of the five holds
  a `javadoc-gate` profile.
- **Two guardrails are reported, not required, and `main` requires only the verdict** — the
  commit-format and pull-request-body checks are required on no branch, and `main`'s ruleset requires
  `docs-review / publish / verdict` but not `docs / docs-lint` or `javadoc / javadoc-gate`. Changing
  either is a ruleset change, not a workflow one.
- **Whether `MatchDslTranspiler` is superseded or a seam to wire** is undecided; its Javadoc states
  that nothing calls it.
