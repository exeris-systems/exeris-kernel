# 1.0 GA scope register

**What this is.** One place that answers "what does 1.0 owe, and is it done?" — because until now
nothing did.

`docs/ROADMAP.md` carries **32 sections with a `**1.0 disposition:**` line** and, measured on
`development/0.12.0`, **exactly one of them also carries a `**Status:**` line**. So the roadmap
records what each item is owed at GA and, for thirty-one of thirty-two, says nothing about whether
it happened. That is not a documentation nit: it is why the 1.0 list gets reconstructed from memory
each time it is asked for, and why an item can fall out of scope leaving no trace. JPMS module naming
was called a P0 GA blocker in the v0.8 readiness audit, appeared in no roadmap section afterwards,
and was noticed again only by someone remembering it.

**What this is not.** Not a second copy of the roadmap. The roadmap owns the *analysis* — the gap,
the resolution, the merge gate. This file owns the *state*, and links back. A row here without a
roadmap section is a row about nothing.

## How a state is decided

Every state is either **verified against the tree** with the check written next to it, or marked
`unverified`. There is no third option, and `unverified` is not a euphemism for "probably fine" —
it means nobody has checked, which for thirty-one items is the honest answer today.

Two false positives were caught while filling in the first pass, and both are the reason the
evidence column exists rather than a status word:

- `schema_version` appears in four main-source files, which reads as "the kernel-owned migration
  ledger exists". It is the **flow snapshot codec's payload version**, unrelated to the table
  migration ledger the roadmap asks for.
- `List<GraphEdgeDescriptor>` appears in five main-source files, which reads as multi-hop traversal.
  `GraphTraversal` still carries **one** `GraphEdgeDescriptor`.

A grep that hits is not evidence. The check has to be one that fails when the thing is absent.

## Explicitly post-1.0

Recorded so they stop being re-litigated: DST harness; systemic flow-control contract; per-tenant
rate limiting; **flow parallel steps as a runtime capability** — the roadmap already rules that the
*statement* of the constraint is 1.0 and the capability is not, which answers a question that has
come up more than once.

## Open decisions that are not yet items

These have no roadmap section and therefore no disposition. They are listed here so the register is
not quietly narrower than the question it answers:

- **Which `preview` SPI surfaces 1.0 promotes**, and what blocks each —
  [RFC-2026-09-02](../rfc/RFC-2026-09-02-preview-spi-promotion.md). Seven Tier 2 capabilities name a
  `preview` kernel SPI, three more depend on one without declaring it, and `…spi.events` and
  `…spi.graph` cannot be promoted at all until an ADR exists, because the matrix defines `stable` as
  requiring one.
- **Whether `ProjectionEngine` grows into the read-model worker** the SDK's `@Projection` describes,
  or whether that belongs to a capability. Unlike flow, graph and events it has **no provider seam**,
  so a deployment cannot substitute another engine — which means growing it is a kernel change, and
  also why no capability can claim it.
- **Whether an alert contract is a new SPI or another `TelemetrySink` shape.** Metrics already have
  both a contract and a binding; alerts have one JFR event and no contract.
- **Who owns partitioning** — plausibly a Kafka driver concern rather than kernel surface.

## How this file stays true

`tools/scope-register-check/scope-register-check.sh` fails when the roadmap and this register
disagree: a `**1.0 disposition:**` with no row here, or a row here naming no roadmap section. It
does **not** check that a state is correct — nothing can — only that nothing is missing from either
side. That is the specific failure this file exists to prevent, and it is the one a human reading two
documents reliably makes.
