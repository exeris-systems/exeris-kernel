# 1.0 GA scope register

**What this is.** One place that answers "what does 1.0 owe, and where does each item stand?"

**The measurement, corrected.** An earlier draft of this file opened by claiming that of 32 roadmap
sections carrying a `**1.0 disposition:**`, exactly one also carried a `**Status:**` line. That was
wrong, and wrong in the way this file exists to prevent: the extractor behind it anchored its match
at the start of the line and most status lines are indented, so it counted one where the answer is
**21 of 31**. Ten carry no state at all. The number went into a PR title before anybody checked it.

So the roadmap is **not** silent about state — it records it per item, in prose, spread across some
three thousand lines. What is actually missing is narrower and still worth fixing:

- **ten dispositioned items with no recorded state at all**, indistinguishable from items whose
  state nobody has written down;
- **no single place to read the twenty-one that do have one**, so the GA picture is reconstructed by
  reading the roadmap end to end;
- and the class this register was really reacting to: **an item with a disposition nowhere at all.**
  JPMS module naming was called a P0 GA blocker in the v0.8 readiness audit, appeared in no roadmap
  section afterwards, and resurfaced only because somebody remembered it. That is now a roadmap
  section with a disposition of its own, which is the fix — a second document describing the gap
  would not have been.

**What this is not.** Not a second copy of the roadmap. The roadmap owns the *analysis* — gap,
resolution, merge gate — and, where it has one, the item's own status. This file is the index over
them, and a row here without a roadmap section is a row about nothing.

## How a state is decided

`*see roadmap*` means the section carries its own status line and the roadmap is authoritative for
it. `unverified` means no state is recorded anywhere and nobody has checked — for ten items that is
the honest answer. Anything else was checked against the tree, with the check named beside it.

Two false positives were caught while filling in the first pass, and they are why the evidence
column exists rather than a status word:

- `schema_version` appears in four main-source files, which reads as "the kernel-owned migration
  ledger exists". It is the **flow snapshot codec's payload version**, unrelated to the table
  migration ledger the roadmap asks for.
- `List<GraphEdgeDescriptor>` appears in five main-source files, which reads as multi-hop traversal.
  `GraphTraversal` still carries **one** `GraphEdgeDescriptor`.

A grep that hits is not evidence. The check has to be one that fails when the thing is absent — and,
per the correction above, so does the instrument that counts the rows.

## Open decisions that are not yet items

No roadmap section, therefore no disposition. Listed so the register is not quietly narrower than
the question it answers:

- **Which `preview` SPI surfaces 1.0 promotes**, and what blocks each —
  [RFC-2026-09-02](../rfc/RFC-2026-09-02-preview-spi-promotion.md). Seven Tier 2 capabilities name a
  `preview` kernel SPI, three more depend on one without declaring it, and `…spi.events` and
  `…spi.graph` cannot be promoted at all until an ADR exists, because the matrix defines `stable` as
  requiring one.
- **Whether `ProjectionEngine` grows into the read-model worker** the SDK's `@Projection` describes,
  or whether that belongs to a capability. Unlike flow, graph and events it has **no provider seam**,
  so a deployment cannot substitute another engine — which means growing it is a kernel change, and
  also why no capability can claim it.
- **Whether an alert contract is a new SPI or another `TelemetrySink` shape.** Metrics already have
  both a contract and a binding; alerts have one JFR event and no contract.
- **Who owns partitioning** — plausibly a Kafka driver concern rather than kernel surface.

Also worth a decision rather than a row: **"Build: The SPI Gate's Baseline Is Hardened On One Line
And Not The Other"** has a roadmap section with Gap, Owner and Resolution and **no disposition**, so
it is out of this register's scope by definition. An earlier draft listed it, because the extractor
invented a disposition for it out of prose belonging to the section above.

## How this file stays true

`tools/scope-register-check/scope-register-check.sh` fails when the roadmap and this register
disagree: a disposition with no row, or a row naming no roadmap section. It matches exact strings
against the generated comment block below rather than fuzzy-matching titles, because a gate that
cries wolf gets skipped.

It does **not** check that a state is correct. Nothing can — which is what `unverified` is for, and
what the correction at the top of this file is an instance of.
